# Add Hangfire as reusable background-job infrastructure

## Context

This repo is a Clean Architecture **starter kit** meant to be reused as the base for future projects — not a one-off app. Today the only background work is `RefreshTokenCleanupService`, a plain `BackgroundService` with a `PeriodicTimer` (`backend/src/StarterKit.Infrastructure/Services/Auth/RefreshTokenCleanupService.cs`). That's adequate for exactly one in-memory timer job on a single-instance deployment, but it doesn't scale to "future project needs a persistent/retryable/monitorable job" without redoing the wiring each time.

Goal: wire Hangfire (server + PostgreSQL storage + dashboard) into `StarterKit.Infrastructure` once, so any future project cloned from this starter kit gets fire-and-forget/delayed/recurring jobs, automatic retries, and a monitoring dashboard for free. Confirmed with the user:
- **Dashboard access**: not exposed to the internet — restricted at the network layer (internal LAN only). No app-level identity check is layered on top; Hangfire's own default (`LocalRequestsOnlyAuthorizationFilter`, loopback-only) would actually be *wrong* here since it'd reject real LAN clients once `UseForwardedHeaders()` rewrites `RemoteIpAddress` to the real client IP. So the dashboard filter list is explicitly emptied (`Authorization = []`), and access control is a deployment/firewall concern, not app code.
- **Reference job**: migrate the existing `RefreshTokenCleanupService` into a Hangfire recurring job, both to prove the wiring works end-to-end and to remove the "runs on every instance" duplication risk `BackgroundService` has if this starter kit is ever deployed multi-instance.

## New file: `backend/src/StarterKit.Infrastructure/Services/Jobs/HangfireExtensions.cs`

New folder `Services/Jobs/` (sibling to `Auth/`, `Caching/`, `Storage/`, etc. — per-concern split convention). `internal static class HangfireExtensions` in the flat root namespace `StarterKit.Infrastructure` (matches the existing convention that `*Extensions` DI-registration classes skip the nested namespace so `DependencyInjection.cs` needs only one `using` — see `AuthExtensions.cs`).

```csharp
internal static IServiceCollection AddBackgroundJobs(this IServiceCollection services, IConfiguration configuration)
{
    string connectionString = configuration.GetConnectionString("DefaultConnection")
        ?? throw new InvalidOperationException("DefaultConnection connection string is missing.");

    services.AddHangfire(config => config
        .SetDataCompatibilityLevel(CompatibilityLevel.Version_180)
        .UseSimpleAssemblyNameTypeSerializer()
        .UseRecommendedSerializerSettings()
        .UsePostgreSqlStorage(
            c => c.UseNpgsqlConnection(connectionString),
            new PostgreSqlStorageOptions { SchemaName = "hangfire" }));

    services.AddHangfireServer();

    services.Configure<RefreshTokenCleanupSettings>(configuration.GetSection(nameof(RefreshTokenCleanupSettings)));
    services.AddScoped<RefreshTokenCleanupJob>();

    return services;
}
```

Reuses the existing `RefreshTokenCleanupSettings` (`backend/src/StarterKit.Application/Common/Settings/RefreshTokenCleanupSettings.cs`) unchanged — `appsettings.json`'s existing `RefreshTokenCleanupSettings` section (`IntervalHours`, `RetentionDays`) keeps working, no config migration needed.

**Deviation from the original plan, found during verification**: recurring-job scheduling does **not** live here. The static `RecurringJob.AddOrUpdate` facade reads `Hangfire.JobStorage.Current`, which is *not* set synchronously by `AddHangfire(...)` as assumed — it's only populated once the DI container is actually built. Calling it inside `AddBackgroundJobs` (a `ConfigureServices`-time method) threw `InvalidOperationException: Current JobStorage instance has not been initialized yet` in every test that spins up the app (confirmed by `dotnet test`). Fixed by moving the recurring-job registration to a new public `DependencyInjection.UseBackgroundJobs(this IApplicationBuilder app)`, called from `Program.cs` after `app.Build()`, resolving the DI-based `IRecurringJobManager` from a scope instead — exactly what Hangfire's own error message recommends. `RefreshTokenCleanupJob` stays `internal` (same-assembly call from `DependencyInjection.cs`); `IServiceCollection.AddBackgroundJobs`/`IApplicationBuilder.UseBackgroundJobs` are the only two public/internal-crossing entry points, mirroring the existing `Add*`(services)/`Use*`(pipeline) split already used elsewhere in `Program.cs` (e.g. `AddOpenApiWithAuth` + `MapOpenApi`).

The `IntervalHours` semantic changes slightly: it now drives a cron expression rather than "N hours after the timer starts." A second issue surfaced here too: Cronos (Hangfire's cron parser) rejects a step ≥ the field's range — `*/24` is invalid for an hour field (0-23) — so the default `IntervalHours = 24` needs the fixed-daily form `0 0 * * *` instead of `0 */24 * * *`; sub-24-hour values still use the step form. Handled with a one-line branch and comment in `UseBackgroundJobs` (see below), not a settings rename.

## Changed file: `backend/src/StarterKit.Infrastructure/DependencyInjection.cs`

Add `services.AddBackgroundJobs(configuration);` to `AddInfrastructure`, and add the new `UseBackgroundJobs` method described above:

```csharp
public static void UseBackgroundJobs(this IApplicationBuilder app)
{
    using IServiceScope scope = app.ApplicationServices.CreateScope();
    IRecurringJobManager recurringJobManager = scope.ServiceProvider.GetRequiredService<IRecurringJobManager>();
    RefreshTokenCleanupSettings cleanupSettings = scope.ServiceProvider
        .GetRequiredService<IOptions<RefreshTokenCleanupSettings>>().Value;

    string cronExpression = cleanupSettings.IntervalHours >= 24
        ? "0 0 * * *"
        : $"0 */{cleanupSettings.IntervalHours} * * *";

    recurringJobManager.AddOrUpdate<RefreshTokenCleanupJob>(
        "refresh-token-cleanup",
        job => job.RunAsync(CancellationToken.None),
        cronExpression);
}
```

## Replace `RefreshTokenCleanupService` → `RefreshTokenCleanupJob`

Delete `backend/src/StarterKit.Infrastructure/Services/Auth/RefreshTokenCleanupService.cs`. Add `RefreshTokenCleanupJob.cs` in the same folder/namespace (`StarterKit.Infrastructure.Services.Auth`):

```csharp
internal sealed class RefreshTokenCleanupJob(
    AppDbContext context,
    IOptions<RefreshTokenCleanupSettings> options,
    ILogger<RefreshTokenCleanupJob> logger)
{
    public async Task RunAsync(CancellationToken ct)
    {
        DateTime cutoff = DateTime.UtcNow.AddDays(-options.Value.RetentionDays);

        int deleted = await context.RefreshTokens
            .Where(t => t.ExpiresAt < cutoff || (t.RevokedAt != null && t.RevokedAt < cutoff))
            .ExecuteDeleteAsync(ct);

        if (deleted > 0)
            logger.LogInformation("Deleted {Count} expired/revoked refresh tokens.", deleted);
    }
}
```

Key differences from the old `BackgroundService`, both intentional:
- `AppDbContext` is injected directly instead of manually creating a scope via `IServiceScopeFactory` — Hangfire's ASP.NET Core job activator already resolves the job class from a fresh DI scope per execution, so the manual scope was redundant here.
- The `try/catch` that logged and swallowed failures is removed — Hangfire's own retry pipeline (default: automatic retries with backoff) now owns failure handling, and failures surface in the dashboard instead of being silently absorbed. This is the actual point of migrating this job (visibility + retries), so the behavior change is intended, not a regression.
