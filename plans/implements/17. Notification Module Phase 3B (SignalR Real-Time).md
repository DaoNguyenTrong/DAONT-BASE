# Notification Module — Phase 3B (SignalR Real-Time)

## Context

`plans/v1/notification-module-architecture.md` mục 5 vẽ nhánh SignalR (`RT`) tách rời khỏi Phase 2, đánh dấu "optional, chỉ khi polling không đủ UX" và "cần backplane nếu scale multi-instance". Phase 1 (in-app + poll), Phase 2 (Hangfire fan-out + Email), Phase 3 (`16. Notification Module Phase 3 (Web Push via FCM).md`, Web Push qua FCM) đã merge. Phase 3B hiện thực nhánh RT đó: đẩy `Notification` mới tới client đang mở tab ngay khi tạo ra, thay vì chờ tối đa 30s (chu kỳ poll hiện tại, `stores/notifications.ts:5`).

**2 quyết định đã chốt trước khi lập plan (theo yêu cầu người dùng, không phải open question)**:
1. **Đẩy real-time đồng bộ ngay trong `NotifyAsync`** — không đi qua `INotificationChannel`/`NotificationDispatcher` (xem lý do ở Quyết định #1).
2. **Chưa cần Redis backplane** — chạy in-memory (single instance), migrate sang `Microsoft.AspNetCore.SignalR.StackExchangeRedis` sau nếu thật sự scale multi-instance.

**Không đổi gì ở REST contract**: không entity mới, không migration, không controller/DTO mới, không cần `OpenApiGenerateDocumentsOnBuild=true` hay `bun run --cwd frontend codegen` — khác Phase 3 (Push), Phase 3B chỉ thêm 1 kênh truyền tải song song, không đổi bất kỳ HTTP endpoint nào.

## Quyết định thiết kế

### 1. SignalR không phải là 1 `INotificationChannel` — phải đẩy đồng bộ trong `NotifyAsync`, song song với Hangfire fan-out

**Ground truth đã verify**: `HangfireExtensions.cs:25-27` gọi `UsePostgreSqlStorage` **không override `QueuePollInterval`** → dùng default của Hangfire.PostgreSql (tài liệu ghi ~15s, chưa tự verify lại với đúng bản `1.21.1` đang dùng — không phải điểm mấu chốt). Điểm mấu chốt thật sự **không nằm ở con số cụ thể**: dù default là 15s hay 2s, đi qua `NotificationDispatcher` vẫn cộng thêm (a) độ trễ poll của queue, **cộng** (b) 1 round-trip `GetByIdAsync` để load lại notification trong dispatcher (`NotificationDispatcher.cs:15-16`) — không có cấu hình nào đưa tổng thời gian này xuống dưới giây, tức là không thể gọi là "real-time" theo đúng nghĩa của tên gọi Phase 3B.

**Giải pháp**: thêm `IRealtimeNotifier` (Application) — gọi trực tiếp trong `NotificationService.NotifyAsync`, **ngay sau `SaveChangesAsync`**, độc lập với/song song với bước enqueue Hangfire (không phụ thuộc, không chặn nhau — 1 bên lỗi không ảnh hưởng bên kia). Nguyên tắc bất biến giữ nguyên từ Phase 1/2: bảng `Notification` vẫn là nguồn sự thật duy nhất; cả push Hangfire (Email/Push) lẫn push SignalR đều chỉ là "hint" bổ sung, chạy **sau khi** row đã commit.

### 2. Layer placement: `NotificationHub` phải `public` và sống ở Infrastructure, không phải API

`IRealtimeNotifier` (interface, Application) — giống `IEmailSender`/`IPushSender`, để Application không biết SignalR.

`SignalRRealtimeNotifier : IRealtimeNotifier` cần `IHubContext<NotificationHub>` để gửi — nghĩa là **`NotificationHub` phải nằm cùng project với `SignalRRealtimeNotifier`** hoặc ở 1 project mà Infrastructure được phép reference. Theo `architecture.md`: "Dependencies flow inward: API → Application → Domain. Infrastructure implements Domain interfaces" — Infrastructure **không được** reference API. Nếu đặt `NotificationHub` ở API (parallel với `Controllers/`, cách làm "chuẩn" hơn về mặt khái niệm vì Hub là 1 request-entry-point giống Controller), `SignalRRealtimeNotifier` ở Infrastructure sẽ không compile được.

**Quyết định**: `NotificationHub` đặt ở **Infrastructure** (`Services/Notifications/NotificationHub.cs`), cùng chỗ với `SignalRRealtimeNotifier`. Verify: `StarterKit.Infrastructure.csproj:9` đã có sẵn `<FrameworkReference Include="Microsoft.AspNetCore.App" />` (đang dùng cho JWT Bearer trong `AuthExtensions.cs`) — SignalR server nằm trong shared framework, Infrastructure tự chứa được Hub mà không cần thêm package. API (`Program.cs`) gọi `app.MapHub<NotificationHub>(...)` — tham chiếu thẳng type cụ thể, khác cách API gọi `INotificationChannel` (luôn qua interface) — nên **`NotificationHub` phải khai báo `public`**, không phải `internal` như `EmailNotificationChannel`/`PushNotificationChannel` (API không có `InternalsVisibleTo` cho Infrastructure — verify: `StarterKit.Infrastructure.csproj` chỉ có `InternalsVisibleTo` cho `StarterKit.Infrastructure.Tests` và `DynamicProxyGenAssembly2`). Đây là ngoại lệ duy nhất trong `Services/Notifications/` cần `public` — cần note rõ khi implement để không bị "sửa lại cho nhất quán" nhầm.

### 3. Auth: tái dùng cookie JWT có sẵn, không cần trick query-string token

`AuthExtensions.cs:60-72` đã có `OnMessageReceived` đọc `access_token` cookie khi header rỗng. WS handshake là 1 request HTTP bình thường — browser tự gửi kèm cookie giống mọi API call có credential khác, vì CORS đã bật `AllowCredentials()` với origin tường minh (`Program.cs:83-90`, `WithOrigins(...).AllowCredentials()`). Trick "token qua query string" (`accessTokenFactory`) chỉ cần khi auth **chỉ** dựa vào header Bearer (browser không set custom header trên WS) — không phải trường hợp ở đây vì cookie đã đủ.

`[Authorize]` trên `NotificationHub` tái dùng `DefaultPolicy` có sẵn (`AuthExtensions.cs:79-84` — JWT Bearer + ApiKey scheme), không cần khai policy riêng.

### 4. Định tuyến theo user: dùng `Clients.User(accountId)`, không cần `IUserIdProvider` tuỳ chỉnh

Verify: `JwtTokenService.GenerateAccessToken` (`JwtTokenService.cs:28`) set `new(ClaimTypes.NameIdentifier, account.Id.ToString())` — đúng claim mà `IUserIdProvider` mặc định của SignalR đọc để định danh `Context.UserIdentifier`. Nên `Clients.User(accountId.ToString())` chạy đúng ngay, tự động gửi tới **mọi** connection của user đó (multi-tab/multi-device), không cần code quản lý Group thủ công.

### 5. Payload: tái dùng `NotificationDto`, truyền `accountId` riêng để định tuyến

`NotificationDto` (`NotificationDto.cs:3`: `Id, Type, Data, IsRead, CreatedAt`) **không có `AccountId`** — cố ý bị `[MapperIgnoreSource(nameof(Notification.AccountId))]` trong `EntityMapper.ToDto(Notification)` vì DTO này vốn chỉ trả cho chính chủ qua REST (`GetMyNotificationsAsync`), không cần AccountId trong payload. Để không phải đổi contract REST hiện có (và không cần OpenAPI/codegen lại), `IRealtimeNotifier.NotifyAsync` nhận `accountId` như 1 tham số **định tuyến** riêng, tách khỏi payload gửi đi:

```csharp
Task NotifyAsync(Guid accountId, NotificationDto notification, CancellationToken cancellationToken);
```

### 6. Backplane: chưa cần Redis (chốt theo yêu cầu #2)

Verify lại tại thời điểm viết plan: `docker-compose.yml` không có Redis; không có k8s/manifest multi-replica trong repo; `CachingExtensions.cs` hiện dùng `AddMemoryCache()` (in-memory, cùng tinh thần) — không có tiền lệ hạ tầng multi-instance nào trong repo này. SignalR mặc định (in-memory) chạy đúng cho 1 instance. Khi nào cần: nếu deploy > 1 instance API phía sau load balancer, phải thêm `Microsoft.AspNetCore.SignalR.StackExchangeRedis` + `.AddStackExchangeRedis(...)` — không làm ở phase này, đúng tinh thần YAGNI đã áp dụng cho Prometheus (`.claude/decisions.md`, 2026-08-03).

### 7. Push realtime lỗi không được làm hỏng `NotifyAsync`

Giống enqueue Hangfire (Phase 2, quyết định #3 của `15. ...md`): bọc riêng trong try/catch, chỉ log — 1 lỗi SignalR (vd hub context tạm thời lỗi) không được biến `NotifyAsync` (đã persist xong) thành lỗi phía caller.

### 8. Frontend: giữ poll 30s làm fallback, tạm dừng khi SignalR đang sống, catch-up khi reconnect

SignalR in-memory **không** giữ lại message gửi trong lúc mất kết nối (khác Hangfire fan-out — bản ghi `Notification` vẫn còn trong DB, chỉ có "hint" real-time bị mất). Vì vậy:
- Khi `onreconnected` — phải gọi lại `fetchUnreadCount()` (REST) để đồng bộ lại số đã có thể bị miss trong lúc mất kết nối, **không** chỉ dựa vào message tiếp theo.
- Poll 30s (`stores/notifications.ts`) **giữ nguyên**, không xoá — nhưng tạm dừng interval khi SignalR đang connected (tránh double-fetch dư thừa), và tự resume khi SignalR đóng hẳn (`onclose`, nghĩa là đã hết lượt tự reconnect) — làm fallback network layer khi WS bị chặn (proxy/firewall công ty, v.v.).
- **Gap cần xử lý tường minh**: `withAutomaticReconnect()` mặc định retry theo backoff `[0, 2, 10, 30]`s trước khi rơi vào `onclose` — nghĩa là trong cửa sổ `onreconnecting` (tới ~30-60s), kết nối đã mất nhưng `onclose` **chưa** fire, nên nếu chỉ resume poll ở `onclose` thì suốt cửa sổ này **không kênh nào** đang giao hàng (poll đã pause từ lúc connected, WS thì đang retry). Phải resume poll ngay tại `onreconnecting`, không đợi tới `onclose`; `onreconnected` sẽ pause lại poll khi WS sống lại (idempotent nhờ dùng `??=` khi set interval — xem code Part 4).

Dùng `EntityMapper.ToDto` đã có sẵn (đang dùng ở `GetMyNotificationsAsync`), không map tay:

```csharp
public sealed class NotificationService(
    IUnitOfWork unitOfWork,
    ICurrentUserService currentUserService,
    IBackgroundJobDispatcher jobDispatcher,
    IRealtimeNotifier realtimeNotifier,
    ILogger<NotificationService> logger) : INotificationService
{
    public async Task NotifyAsync(NotificationParams request, CancellationToken cancellationToken)
    {
        Notification notification = Notification.Create(request);
        await unitOfWork.Repository<Notification, Guid>().AddAsync(notification, cancellationToken);
        await unitOfWork.SaveChangesAsync(cancellationToken);

        try
        {
            await realtimeNotifier.NotifyAsync(
                notification.AccountId, EntityMapper.ToDto(notification), cancellationToken);
        }
        catch (Exception exception)
        {
            // Bản ghi in-app đã commit — lỗi đẩy realtime không được biến 1 NotifyAsync
            // thành công thành lỗi phía caller. Client vẫn thấy notification qua poll fallback.
            logger.LogError(exception, "Failed to push realtime notification {NotificationId}", notification.Id);
        }

        try
        {
            jobDispatcher.Enqueue<INotificationDispatcher>(
                dispatcher => dispatcher.DispatchAsync(notification.Id, CancellationToken.None),
                NotificationQueues.Default);
        }
        catch (Exception exception)
        {
            logger.LogError(exception, "Failed to enqueue dispatch for notification {NotificationId}", notification.Id);
        }
    }

    // ... GetMyNotificationsAsync / GetUnreadCountAsync / MarkAsReadAsync / MarkAllAsReadAsync giữ nguyên ...
}
```

(cần thêm `using StarterKit.Application.Common.Mappings;` nếu chưa có — kiểm tra lại lúc code, file hiện tại có thể đã import sẵn cho `GetMyNotificationsAsync`.)

### Edit: `frontend/src/stores/notifications.ts`

Mở rộng store hiện có (không tạo composable/store mới — store này đã sở hữu toàn bộ state cross-cutting của notification, đúng pattern `api-contract.md` đã mô tả cho side-effect ngoài generated client). Thêm 1 `HubConnection`, gate lại `resume()`/interval theo trạng thái kết nối:

```ts
import * as signalR from '@microsoft/signalr'
import type { Notification } from '@/api/types'

let connection: signalR.HubConnection | null = null
let isRealtimeConnected = false

function pause() {
  if (intervalHandle) clearInterval(intervalHandle)
  intervalHandle = null
}

function resume() {
  fetchUnreadCount()
  if (!isRealtimeConnected) {
    intervalHandle ??= setInterval(fetchUnreadCount, POLL_INTERVAL_MS)
  }
}

async function connectRealtime() {
  connection = new signalR.HubConnectionBuilder()
    .withUrl(`${import.meta.env.VITE_API_BASE_URL}/hubs/notifications`, { withCredentials: true })
    .withAutomaticReconnect()
    .build()

  connection.on('ReceiveNotification', (_dto: Notification) => {
    unreadCount.value += 1
  })

  connection.onreconnecting(() => {
    // Đang trong cửa sổ retry (backoff mặc định tới ~30-60s) — CHƯA phải onclose, nhưng
    // kết nối đã mất, nên phải resume poll ngay ở đây, không đợi onclose, nếu không sẽ có
    // khoảng trống không kênh nào đang giao hàng (xem Quyết định #8).
    isRealtimeConnected = false
    resume()
  })

  connection.onreconnected(() => {
    isRealtimeConnected = true
    pause() // dừng poll trở lại khi WS sống lại
    fetchUnreadCount() // catch-up: bù các notification có thể miss lúc mất kết nối
  })

  connection.onclose(() => {
    isRealtimeConnected = false
    resume() // fallback: SignalR hết lượt tự reconnect (hoặc chưa từng start được), quay lại poll
  })

  try {
    await connection.start()
    isRealtimeConnected = true
    pause()
  } catch {
    isRealtimeConnected = false // start() lỗi (vd WS bị chặn) — poll vẫn chạy như trước, không throw lên caller
  }
}

async function disconnectRealtime() {
  isRealtimeConnected = false
  await connection?.stop()
  connection = null
}
```

`unreadCount.value += 1` thay vì gọi lại `fetchUnreadCount()` mỗi lần nhận message — tránh round-trip REST không cần thiết cho trường hợp phổ biến nhất (nhận đúng 1 notification mới); độ lệch nếu có (vd 2 tab cùng mark-read đúng lúc) tự sửa lại ở lần `fetchUnreadCount()` kế tiếp (mark-as-read, hoặc reconnect catch-up).

## Decision log

Sau khi implement xong, sẽ đề xuất các entry sau cho `.claude/decisions.md` (draft, xin xác nhận trước khi ghi theo đúng gate rule — chưa làm ở bước lập plan này):

1. **SignalR push chạy đồng bộ trong `NotifyAsync`, không phải 1 `INotificationChannel` qua Hangfire fan-out** — vì Hangfire.PostgreSql poll interval mặc định (~15s, không override) sẽ làm mất ý nghĩa "real-time" nếu đi qua đường đó.
2. **`NotificationHub` đặt ở Infrastructure (không phải API), khai `public`** — vì `SignalRRealtimeNotifier` (Infrastructure) cần `IHubContext<NotificationHub>`, và Infrastructure không được reference API (ngược hướng phụ thuộc); `public` vì API's `Program.cs` cần `MapHub<NotificationHub>` bằng type cụ thể, không qua interface.
3. **Chưa thêm Redis backplane, chạy SignalR in-memory single-instance** — repo hiện không có hạ tầng multi-instance (không Redis, không k8s/replica), cache hiện tại cũng in-memory (`AddMemoryCache`); migrate sang `StackExchangeRedis` khi thật sự cần scale ngang.
