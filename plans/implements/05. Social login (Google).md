# Phase 4: Social login (Google)

## Context

Backend has supported Google credential-forwarding login since PR #13 (`POST /api/auth/external/{provider}`, `authApi.externalLogin()` already implemented and unused on the frontend since Phase 1 of this same effort). Phases 1-3 shipped the email-verification UI (`RegisterView`, `VerifyEmailView`, `useApiAction`, `ResendVerificationForm`) but never wired up the actual "Continue with Google" button `plans/v1/frontend-auth-upgrade.md` originally scoped for Phase 4. This closes that gap — the last piece of the auth-upgrade effort.

The backend's provider is registered conditionally (`ExternalAuthSettings:Google:ClientId` optional, no fail-fast) so deployments without Google configured keep working; the frontend needs to mirror that — no client ID configured, no button shown, not a broken button that always fails.

## Approach

### 1. Type declarations — `frontend/env.d.ts`

Extend the existing hand-written ambient-types file (already has `ImportMetaEnv` from the runtime-config work, and the `virtual:svg-icons-register` module pattern to follow) rather than adding a new typings file:

```ts
interface ImportMetaEnv {
  readonly VITE_API_BASE_URL: string
  readonly VITE_GOOGLE_CLIENT_ID?: string
}

interface CredentialResponse {
  credential: string
}

interface Window {
  google?: {
    accounts: {
      id: {
        initialize(config: { client_id: string; callback: (response: CredentialResponse) => void }): void
        renderButton(parent: HTMLElement, options: Record<string, unknown>): void
      }
    }
  }
}
```
No `@types/google.accounts` or any npm package needed — Google Identity Services (GSI) is loaded as a plain `<script>`, not an npm module, and we only call two of its methods.

### 2. `frontend/.env.example`

Add `VITE_GOOGLE_CLIENT_ID=` (empty, documented as optional — same convention as the rest of the file).

### 3. `frontend/src/composables/use-google-auth.ts` (new)

All the actual logic — deliberately separated from the GSI/DOM concerns in step 4, so it's testable with plain msw mocks like every other composable in this codebase, no fake `window.google` needed:

```ts
export function useGoogleAuth() {
  const router = useRouter()
  const { t } = useI18n()
  const { isLoading, error, run } = useApiAction()
  const showResendVerification = ref(false)

  async function handleCredential(credential: string) {
    showResendVerification.value = false

    const result = await run(
      () => authApi.externalLogin('google', { credential }),
      {
        onCode: {
          ExternalLoginEmailNotConfirmed: () => {
            error.value = t('auth.googleEmailNotConfirmed')
            showResendVerification.value = true
          },
          ExternalLoginEmailNotVerifiedByProvider: () => {
            error.value = t('auth.googleEmailNotVerifiedByProvider')
          },
        },
        fallbackMessage: t('auth.googleLoginFailed'),
      },
    )

    if (result) {
      await router.push(useHomeRoute())
    }
  }

  return { isLoading, error, showResendVerification, handleCredential }
}
```

Error-code coverage (all 4 backend codes confirmed in `ApplicationMessages.cs`):
- `ExternalLoginEmailNotConfirmed` (409, matched email exists locally but unconfirmed — backend refuses to auto-link) — the one genuinely actionable case, gets its own message **and** reuses `ResendVerificationForm` exactly like `LoginView`'s existing `EmailNotConfirmed` branch, so the user has a way forward instead of a dead end.
- `ExternalLoginEmailNotVerifiedByProvider` (401, Google itself hasn't verified the account's email — rare, e.g. some Workspace setups) — distinct message since "try again" wouldn't help; nothing else to do differently.
- `ExternalLoginProviderNotSupported` (400, misconfiguration — frontend has a client ID but backend doesn't) and `InvalidExternalCredential` (401, malformed/expired id_token) — both fall through to the generic `fallbackMessage`; no clearer message would help either case.

### 4. `frontend/src/components/GoogleLoginButton.vue` (new)

Owns script-loading and GSI wiring only; delegates all result-handling to `useGoogleAuth()`.

```ts
const clientId = import.meta.env.VITE_GOOGLE_CLIENT_ID
const buttonEl = ref<HTMLDivElement | null>(null)
const localeStore = useLocaleStore()
const { isLoading, error, showResendVerification, handleCredential } = useGoogleAuth()

let scriptPromise: Promise<void> | null = null

function loadGsiScript(): Promise<void> {
  if (window.google?.accounts?.id) return Promise.resolve()
  if (scriptPromise) return scriptPromise
  scriptPromise = new Promise((resolve, reject) => {
    const script = document.createElement('script')
    script.src = 'https://accounts.google.com/gsi/client'
    script.async = true
    script.onload = () => resolve()
    script.onerror = () => reject(new Error('Failed to load Google Identity Services'))
    document.head.appendChild(script)
  })
  return scriptPromise
}

onMounted(async () => {
  if (!clientId) return
  try {
    await loadGsiScript()
    window.google!.accounts.id.initialize({
      client_id: clientId,
      callback: (response) => void handleCredential(response.credential),
    })
    if (buttonEl.value) {
      window.google!.accounts.id.renderButton(buttonEl.value, {
        theme: 'outline',
        size: 'large',
        locale: localeStore.currentLocale,
      })
    }
  } catch {
    error.value = t('auth.googleLoginFailed')
  }
})
```

Template: `v-if="clientId"` wraps everything (component renders nothing at all when unconfigured — matches the backend's own "provider just isn't registered" philosophy instead of showing a button that always fails); a `<div ref="buttonEl" />` for GSI to render its own native button into, an error `<n-alert>`, and `<ResendVerificationForm v-if="showResendVerification" />` below it.

**Why the `window.google?.accounts?.id` early-return in `loadGsiScript` matters beyond dedup**: it's also what makes the component testable at all — tests can `vi.stubGlobal('google', { accounts: { id: { initialize: vi.fn(), renderButton: vi.fn() } } })` *before* mounting, and the component will use that stub directly without ever touching the network (jsdom/happy-dom can't load the real script anyway). No GSI mocking library needed.

**Button label is not an i18n key** — GSI renders its own button text based on the `locale` option (Google translates "Continue with Google" itself); we don't own that string. Only the surrounding "or continue with" divider is ours.

### 5. Wire into `LoginView.vue` and `RegisterView.vue`

Add, as siblings *after* the closing `</form>` (not inside it — GSI's button isn't a form submit, keeping it outside avoids any accidental Enter-key/submit interaction):

```html
<div class="flex items-center gap-3">
  <div class="h-px flex-1 bg-surface-200 dark:bg-surface-800" />
  <span class="text-xs text-surface-500 dark:text-surface-400">{{ t('auth.orContinueWith') }}</span>
  <div class="h-px flex-1 bg-surface-200 dark:bg-surface-800" />
</div>
<GoogleLoginButton />
```

In `RegisterView.vue` this only belongs in the `v-else` (form) branch, not the post-registration success panel — registering via Google doesn't need the "check your email" step at all (`ExternalLoginAsync` creates the account with `EmailConfirmed = true` directly), so showing it there would be misleading.

**Adjacent, small, worth doing in the same pass**: `LoginView.vue` currently has no link to `/register` at all (confirmed while reading the file — `RegisterView.vue` has a "back to login" `RouterLink` but nothing exists in the other direction). Add a matching "Don't have an account? Register" link, same style as `RegisterView`'s `auth.backToLogin`. Unrelated to Google specifically, but it's a real, currently-broken navigation gap on the exact page this phase is already touching.

### 6. i18n — flat under `auth.*`

New keys: `orContinueWith`, `googleEmailNotConfirmed`, `googleEmailNotVerifiedByProvider`, `googleLoginFailed`, and `registerLink` (or similar) for the new LoginView → RegisterView link, added to both `LocaleSchema` (`en.ts`) and the `en`/`vi` value objects — same three-places-per-key discipline as every prior phase (enforced by `bun run build`'s type-check).

## Verification

**Unit tests (vitest + msw)**:
- `frontend/tests/unit/composables/use-google-auth.test.ts` (new, mirrors `use-api-action.test.ts`'s `withSetup()` style — needs a router since `handleCredential` calls `router.push`): success (mock 200 `AuthResponse`) → redirects home; `ExternalLoginEmailNotConfirmed` → `error` set to the specific message, `showResendVerification === true`; `ExternalLoginEmailNotVerifiedByProvider` → distinct message, `showResendVerification` stays false; `ExternalLoginProviderNotSupported`/`InvalidExternalCredential` → generic fallback message.
- `frontend/tests/components/GoogleLoginButton.test.ts` (new): stub `window.google` via `vi.stubGlobal` before mount; with `VITE_GOOGLE_CLIENT_ID` stubbed present (`vi.stubEnv`) → `initialize`/`renderButton` called with the expected `client_id`; with the env var absent (default) → nothing renders, `initialize`/`renderButton` never called.
- Extend `LoginView.test.ts`/`RegisterView.test.ts` minimally: assert `GoogleLoginButton` is present in the rendered tree (existence only — its own internals are covered by its dedicated test above).
- `bun run --cwd frontend test:run` full pass; `bun run --cwd frontend build` clean (catches `LocaleSchema` drift as always).

**Live verification — split into what I can self-verify vs. what needs you**:
- Self-verifiable via Playwright without a real Google account: page layout with the button container present/absent based on whether a client ID is configured; the divider renders correctly in both locales; the new LoginView → RegisterView link works; confirm no console errors when `VITE_GOOGLE_CLIENT_ID` is unset (component silently no-ops, matching the "not configured" backend philosophy).
- **Needs your input, can't be faked** (same limitation flagged in the original Phase 1 plan doc): a real Google Cloud OAuth Client ID (Web application type, Authorized JavaScript origin matching whatever dev port is used) to actually exercise the popup → credential → backend round trip end-to-end. I can verify the backend side of a *malformed* credential independently (already proven live in the Phase 2 backend work — `Google.Apis.Auth` correctly rejects it with `InvalidExternalCredential`), but a *valid* end-to-end login needs a real account and client ID from you.

## Not in this phase (explicitly deferred)

- Extending the runtime-config mechanism (`public/config.json`) to also cover `googleClientId` alongside `apiBaseUrl` — same rationale (one build, multiple environments, each with its own registered OAuth origin) applies here, arguably even more so since Google Client IDs are tied to specific origins per Google Cloud Console config. Worth doing, but it's a separable enhancement to already-shipped infrastructure, not required to ship Google login itself — flagging it rather than bundling it in to keep this phase focused.
- Microsoft/GitHub providers — already deferred behind the same backend `IExternalAuthProvider` abstraction per `.claude/decisions.md`; frontend would need a near-identical `*LoginButton.vue` per provider when that happens, not part of this phase.
