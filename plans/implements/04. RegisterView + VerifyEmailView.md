# Phase 3: RegisterView + VerifyEmailView

## Context

Phases 1-2 of the frontend auth upgrade are merged: `authApi` already has `register()`, `verifyEmail()`, `resendVerification()` wired to the backend's email-verification contract (register no longer auto-logs-in; login rejects unconfirmed accounts with a `code: 'EmailNotConfirmed'` that `LoginView.vue` already branches on to show `ResendVerificationForm.vue`). What's missing is the actual registration and email-verification UI — today `/register` is just a `redirect: { name: 'login' }` stub, and `/verify-email` (the link the backend emails) doesn't exist as a route at all. This phase closes that gap: a real registration form and a page that consumes the verification link's `?token=`, so the register → verify-email → login loop (currently only reachable via curl) becomes usable end-to-end from the browser.

Reviewing the existing views while planning this surfaced a second problem worth fixing in the same pass: every form (`LoginView.vue`, `ProfileDialog.vue`, `ProfileView.vue`) hand-rolls its own `try { isLoading=true; ... } catch (error) { if (error instanceof ApiError) {...} else {...} } finally { isLoading=false }` block, each reimplementing the same "is this a validation error, a specific known code, or something generic" branching. Backend PR#14 unified error output through one shared `ApiProblemDetailsFactory` specifically so callers could branch on a stable `code` instead of parsing prose — but the frontend never got the equivalent consolidation, so every new form (this phase's `RegisterView` included) was on track to add a fourth copy of the same scattered logic. This phase introduces a shared composable that both new views use, mirroring the backend's "one dispatch point" shape. **Scope decision (confirmed with user):** only the two new views adopt it now; retrofitting `LoginView`/`ProfileDialog`/`ProfileView` onto it is a deliberate follow-up, not bundled here, so this phase doesn't touch/re-test currently-working forms.

## Approach

### 1. Router (`frontend/src/router/index.ts`)

Replace the existing `/register` redirect entry, and add `/verify-email` next to it (same position, between `/login` and the catch-all):

```ts
{
  path: '/register',
  name: 'register',
  component: () => import('@/views/RegisterView.vue'),
  meta: { guestOnly: true },
},
{
  path: '/verify-email',
  name: 'verify-email',
  component: () => import('@/views/VerifyEmailView.vue'),
  // deliberately no guestOnly — an already-authenticated user may click a
  // stale verification link from a different session; let the view run
  // instead of bouncing them home before the token is even processed.
},
```
No changes needed to the `beforeEach` guard itself.

### 2. Extract `mapValidationErrors` — `frontend/src/lib/validation.ts` (new)

This helper is currently copy-pasted in **two** places (`frontend/src/components/ProfileDialog.vue:29` and `frontend/src/views/ProfileView.vue:26`, identical logic), and the new composable (§3) needs it as a third consumer — extract it:

```ts
export function mapValidationErrors(errors?: Record<string, string[]>): Record<string, string> {
  if (!errors) return {}
  return Object.fromEntries(
    Object.entries(errors).map(([field, messages]) => [field.toLowerCase(), messages[0] ?? '']),
  )
}
```

`src/lib/**` is already in `vite.config.ts`'s `AutoImport.dirs` (confirmed), so no import statements are needed anywhere — delete the local function from both `ProfileDialog.vue` and `ProfileView.vue`; the auto-imported one resolves under the same name with zero other call-site changes (both files keep using their own `try/catch` for now, per the scope decision above — only the *helper* is shared today, not the lifecycle wrapper in §3). Backend's `errors` dict keys already arrive lowercase (verified live during PR#14 testing), so `.toLowerCase()` is a harmless no-op safety net here, not load-bearing — keep it for consistency with the existing behavior.

### 3. Shared error-dispatch composable — `frontend/src/composables/use-api-action.ts` (new)

Centralizes the repeated try/catch/loading-flag/code-branching shape into one place, mirroring the backend's `ApiProblemDetailsFactory` — one dispatch point instead of scattered per-component logic:

```ts
export function useApiAction() {
  const isLoading = ref(false)
  const error = ref<string | null>(null)
  const fieldErrors = ref<Record<string, string>>({})

  async function run<T>(
    action: () => Promise<T>,
    options: {
      onCode?: Record<string, (detail: string | undefined) => void>
      fallbackMessage?: string
    } = {},
  ): Promise<T | undefined> {
    if (isLoading.value) return undefined

    isLoading.value = true
    error.value = null
    fieldErrors.value = {}

    try {
      return await action()
    } catch (caught) {
      if (caught instanceof ApiError) {
        const code = caught.problem.code
        const handler = code ? options.onCode?.[code] : undefined

        if (code === 'ValidationFailed') {
          fieldErrors.value = mapValidationErrors(caught.problem.errors)
        } else if (handler) {
          handler(caught.problem.detail)
        } else {
          error.value = caught.problem.detail ?? options.fallbackMessage ?? i18n.global.t('errors.requestFailed')
        }
      } else {
        error.value = options.fallbackMessage ?? i18n.global.t('errors.requestFailed')
      }
      return undefined
    } finally {
      isLoading.value = false
    }
  }

  function clearFieldError(field: string) {
    if (!(field in fieldErrors.value)) return
    const next = { ...fieldErrors.value }
    delete next[field]
    fieldErrors.value = next
  }

  return { isLoading, error, fieldErrors, run, clearFieldError }
}
```

Design notes:
- `run()` self-guards against concurrent calls (`if (isLoading.value) return`), so callers don't need their own `isSubmitting` check before calling it.
- `error` is a plain `string | null`, matching every existing `submitError`/`loadError` ref shape in the codebase today — bind it straight into an `<n-alert>`.
- `onCode` is an optional map from a specific `code` to a handler receiving `detail` — lets a caller attach a 409 to a specific field (`fieldErrors.value.username = ...`) instead of the generic top-level `error`. `ValidationFailed` is handled generically inside the composable itself (via `mapValidationErrors`) since that dispatch never varies by caller.
- Falls back to `i18n.global.t('errors.requestFailed')` (same global-i18n-instance access pattern already used in `frontend/src/api/client.ts`, auto-imported via `src/plugins/**`) when a caller supplies no `fallbackMessage` — so forgetting to pass one degrades gracefully instead of showing a blank error.
- `ApiError` and `mapValidationErrors` need no explicit imports here (both auto-imported per `vite.config.ts`), consistent with how every other view already uses `ApiError` today.

New test: `frontend/tests/unit/composables/use-api-action.test.ts`, following the existing `frontend/tests/unit/composables/use-*.test.ts` convention (e.g. `use-health-status.test.ts`) — cover: success passes the resolved value through; `ValidationFailed` populates `fieldErrors` via `mapValidationErrors`; a matching `onCode` handler fires instead of setting `error`; an unmatched code falls back to `error` = detail; a non-`ApiError` throw falls back to `fallbackMessage` or the i18n default; concurrent `run()` calls while `isLoading` is true are ignored; `clearFieldError` removes only the named field.

### 4. `frontend/src/views/RegisterView.vue` (new)

Page shell: copy `LoginView.vue`'s bare-page markup verbatim (outer `<section class="relative min-h-screen ...">` + top-right `<AppControls />` + centered `max-w-md` card with the `h-1 bg-primary-500` accent strip and `p-6 sm:p-8` content padding) — **not** `NotFoundView.vue`'s shell, which uses a different card style (`max-w-2xl`, no accent strip).

Fields: `name`, `username`, `email`, `password`, `phone?`, `position?`, `address?` — matches `RegisterRequest` exactly. Build them inline (do **not** reuse `AccountForm.vue` — it's a pure presentational component with zero validation/error-display slots, wrong fit here). Reuse existing `accounts.*` i18n keys for all 7 field labels/placeholders (`accounts.name`/`accounts.namePlaceholder`, etc. — already a complete matching set, single source instead of duplicating under a new namespace).

**Two-tier validation, merged for display:**
```ts
const form = reactive({ name: '', username: '', email: '', password: '', phone: '', position: '', address: '' })
const hasSubmitted = ref(false)
const registered = ref<RegisterResult | null>(null) // non-null => success panel

const { isLoading: isSubmitting, error: submitError, fieldErrors, run, clearFieldError } = useApiAction()

const nameClientError = computed(() => !hasSubmitted.value || form.name.trim() ? null : t('auth.nameRequired'))
// ...usernameClientError, emailClientError (required + basic format check), passwordClientError (required + length < 8 → t('auth.passwordTooShort'))

const nameError = computed(() => fieldErrors.value.name ?? nameClientError.value)
// ...same merge pattern per field — server (from the composable) wins, doesn't depend on hasSubmitted

const hasValidationErrors = computed(() =>
  Boolean(nameClientError.value || usernameClientError.value || emailClientError.value || passwordClientError.value)
) // built ONLY from the client tier — see note below
```
**Correctness note (why the gate must stay client-tier-only):** if `hasValidationErrors` read the merged `xxxError` computeds instead, a persistent `fieldErrors` entry (e.g. "username already exists") would keep the gate permanently true, since nothing clears it except editing that field — the user would never be able to resubmit. Each field's input needs a change handler that calls the composable's `clearFieldError('username')` the moment the user edits it, so editing a field with a server error falls back to a fresh client-tier check.

**Submit handler**, using `run()` from §3:
```ts
async function handleSubmit() {
  hasSubmitted.value = true
  if (hasValidationErrors.value) return

  const result = await run(
    () => authApi.register({
      name: form.name.trim(), username: form.username.trim(), email: form.email.trim(),
      password: form.password,
      phone: form.phone.trim() || undefined, position: form.position.trim() || undefined, address: form.address.trim() || undefined,
    }),
    {
      onCode: {
        AccountUsernameAlreadyExists: (detail) => {
          fieldErrors.value = { ...fieldErrors.value, username: detail ?? t('auth.usernameAlreadyExists') }
        },
        AccountEmailAlreadyExists: (detail) => {
          fieldErrors.value = { ...fieldErrors.value, email: detail ?? t('auth.emailAlreadyExists') }
        },
      },
      fallbackMessage: t('auth.registerFailed'),
    },
  )

  if (result) registered.value = result
}
```
The two 409 branches attach to their specific field instead of a generic top-level alert — this precision is exactly what the unified `code` field (PR#14) was built for, and is now expressed once in `useApiAction` instead of being reimplemented per view.

**Success state:** `registered.value` (non-null) swaps the template from the form (`v-if="!registered"`) to a success panel (`v-else`) in the same view — no redirect (register doesn't issue tokens). Panel shows `t('auth.registerSuccessMessage', { email: registered.email })`, a "back to login" link, and an embedded `<ResendVerificationForm />` (confirmed with user) so a user whose first email doesn't arrive isn't stranded.

### 5. `frontend/src/views/VerifyEmailView.vue` (new)

Same page shell as RegisterView/LoginView.

```ts
const route = useRoute()
const router = useRouter()
const { t } = useI18n()

const status = ref<'verifying' | 'error'>('verifying')
const { error: errorMessage, run } = useApiAction()

function extractToken(raw: unknown): string | null {
  return typeof raw === 'string' && raw.trim().length > 0 ? raw : null
}

onMounted(async () => {
  const token = extractToken(route.query.token)
  if (!token) {
    status.value = 'error'
    errorMessage.value = t('auth.verifyEmailMissingToken')
    return
  }

  const result = await run(
    () => authApi.verifyEmail({ token }), // setAuth() already runs inside authApi.verifyEmail()
    {
      onCode: {
        EmailVerificationTokenInvalidOrExpired: () => { errorMessage.value = t('auth.verifyEmailInvalidToken') },
      },
      fallbackMessage: t('auth.verifyEmailFailed'),
    },
  )

  if (result) await router.push(useHomeRoute())
  else status.value = 'error'
})
```
This is the second consumer of `useApiAction` and deliberately not a form submit — using the same composable for an on-mount async action (not just form submits) is the concrete proof it's actually general, not a register-specific helper in disguise.

Only **two** rendered states (`verifying`, `error`) — success is a redirect, not a display state, so no template branch is needed for it. Template: `v-if="status === 'verifying'"` → spinner + `t('auth.verifyingEmail')`; `v-else` → error alert with `errorMessage` + `<ResendVerificationForm />` (always shown in the error branch — simpler than sub-branching on which error it was, and harmless for the generic-failure case too).

`route.query.token` is `string | (string|null)[] | undefined` per vue-router — `extractToken` narrows it, treating arrays/blank strings as "no token."

### 7. Test helper change — `frontend/tests/helpers/render.ts`

`renderComponent` currently hardcodes `createMemoryHistory({ initialEntries: ['/'] })`. Add an optional `initialRoute?: string` to `RenderComponentOptions`, threaded into `initialEntries: [initialRoute ??
