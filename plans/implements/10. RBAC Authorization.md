# RBAC Authorization (per-organization custom roles)

## Context

`OrganizationMember.Role` is currently a hardcoded 3-value `OrganizationRole` enum (Owner/Admin/Member), checked imperatively and inline throughout `OrganizationService`. The user wants proper RBAC: a fixed permission catalog, roles that bundle permissions, and each organization authoring its own custom roles (chosen deliberately over a global role catalog or a seed-only hybrid — logged in `.claude/decisions.md`, 2026-08-02 "Authorization: switch to RBAC with per-organization custom roles"). This plan is the execution of that decision.

Everything below preserves existing codebase conventions verified during research: the `Create(Params)`/`Update(Params)` entity factory pattern, zero navigation properties (scalar FK props only, joined manually in application code), soft-delete via `IsActive`/`Deactivate()`, `IdGenerator.NewUuidV7()`, hand-rolled imperative authorization (no ASP.NET policy-based auth anywhere in this codebase today), and permission resolution via a short-TTL cache mirroring `ITenantAccessService`/`TenantAccessService` — **not** JWT-embedded, per the existing `org_id` decision (2026-08-02) which chose per-request re-verification specifically so revocation takes effect within seconds.

## Design Decisions

1. **Permission representation — string constants, not a DB table.** New `Permissions` static class (`public const string OrganizationManage = "organizations.manage";`), same shape as `ApplicationMessages`. `RolePermission.PermissionCode` is a plain `varchar(100)` holding the string directly — no `Permission` table/FK, since the catalog is fixed in code and never queried from the DB side, only compared by value. `GET /api/permissions` serves the catalog from the in-memory constant list.
2. **Enforcement stays hand-rolled** (no `[Authorize(Policy=...)]`) — this change already touches every method of `OrganizationService`; adding policy-based auth simultaneously would compound risk for no benefit since checks are already centralized in one service. Documented as a future option, out of scope here.
3. **Owner invariant.** `Role` gets a nullable `SystemRoleKind` enum column (`Owner`/`Admin`/`Member` — the old enum, repurposed as an immutability marker, never assigned to a member directly). System roles are seeded per-org, non-deletable, non-editable (enforced in `RoleService`, not the entity — same division of responsibility as today's last-owner check). "Can't remove/demote the last Owner" becomes "can't leave zero active members holding the role with `SystemRoleKind == Owner`" — precise and cheap, unlike the much harder "last member holding permission X" (breaks the moment two custom roles both grant that permission).
   **Owner's permission set is resolved dynamically, never stored**: if the caller holds any role with `SystemRoleKind == Owner`, `PermissionResolver` short-circuits to `Permissions.All` — no `RolePermission` rows exist for Owner. This makes Owner future-proof: if seeded as static rows, every existing org's Owner role would silently miss any permission added to the catalog later (system roles are immutable, no backfill path). Only Admin (seeded with `OrganizationMembersManage`) and Member (none) get real `RolePermission` rows.
   Note: a manager (Owner or Admin) granting the Owner role to someone else is existing behavior, not new privilege escalation — today's `EnsureManagerAsync` already lets an Admin promote another member to `OrganizationRole.Owner`.
4. **Resolution + caching**: new `IPermissionResolver` (Application) / `PermissionResolver` (Infrastructure), structurally identical to `TenantAccessService` — same `ICacheService.GetOrSetAsync` + TTL-settings pattern, same `InvalidateMemberAsync`/`InvalidateOrganizationAsync` shape, registered in the same `AuthExtensions.cs`. Because it needs a 4-table hop (member → OrganizationMemberRole → Role → RolePermission), it queries `AppDbContext` directly instead of `IUnitOfWork`/generic repo, following the verified `IAuditLogRepository`/`AuditLogRepository` precedent (`backend/src/StarterKit.Infrastructure/Persistence/Repositories/AuditLogRepository.cs`): hand-written LINQ joins with `AsNoTracking()`, interface in Application, implementation in Infrastructure.
5. **Migration/backfill**: two migrations in the same PR (no dual-write phase needed — no live tenant traffic to protect).
   - **`AddRbacTables`**: creates `roles`, `role_permissions`, `organization_member_roles` + a `migrationBuilder.Sql(...)` backfill: for every existing org, insert its 3 system roles, the Admin role's `OrganizationMembersManage` permission row, and `organization_member_roles` rows mapping every existing `organization_members.Role` value to the matching system role of the same org. `organization_members.Role` column is left in place.
   - **`DropOrganizationMemberRoleColumn`**: drops the column, applied only once no code path reads/writes it (i.e. after the Backend Services phase below).
6. **API surface** (nested under the existing `OrganizationsController`, consistent with today's `/members` sub-resource pattern, plus one new controller):
   - `GET /api/permissions` — static catalog, any authenticated user.
   - `GET /api/organizations/{id}/roles` — any active member (same read bar as viewing members today).
   - `POST /api/organizations/{id}/roles` — requires `Permissions.OrganizationRolesManage`.
   - `PATCH /api/organizations/{id}/roles/{roleId}` / `DELETE .../{roleId}` — same permission; 403 if role is system.
   - `POST /api/organizations/{id}/members` — `AddMemberRequest.Role` (enum) → `RoleIds: Guid[]` (non-empty).
   - `PATCH /api/organizations/{id}/members/{accountId}` — body `{ role }` → `{ roleIds: Guid[] }`.

## Backend

### Domain (`backend/src/StarterKit.Domain/Entities/`)

- Delete `OrganizationRole.cs`.
- New `SystemRoleKind.cs`: `enum SystemRoleKind { Owner, Admin, Member }`.
- New `Role.cs`: `RoleParams(Guid OrganizationId, string Name, SystemRoleKind? SystemRoleKind = null)`, standard `BaseEntity<Guid>` + `Create`/`Update` factory (mirrors `Organization.cs`). `Update()` throws `DomainException(DomainMessages.RoleNameRequired)` on blank name.
- New `RolePermission.cs`: `RolePermissionParams(Guid RoleId, string PermissionCode)` — plain join entity, same `Create`/`Update` pattern as every other entity (this is the codebase's first many-to-many join; no special handling needed beyond the standard shape).
- New `OrganizationMemberRole.cs`: `OrganizationMemberRoleParams(Guid OrganizationMemberId, Guid RoleId)` — same shape.
- Edit `OrganizationMember.cs`: `OrganizationMemberParams` drops `Role`; entity drops the `Role` property. `Deactivate()`/`Reactivate()`/`IsActive` unchanged.
- Edit `DomainMessages.cs`: add `RoleNameRequired`.

### Application layer

- New `Common/Authorization/Permissions.cs` — exactly 3 constants, one per real check that exists today plus role management: `OrganizationManage`, `OrganizationMembersManage`, `OrganizationRolesManage`, plus `Permissions.All`.
- New `Common/Authorization/SystemRoleDefaults.cs` — `IReadOnlyDictionary<SystemRoleKind, IReadOnlyList<string>>`: `Admin → [OrganizationMembersManage]`, `Member → []`. No entry for `Owner` (handled dynamically, see Decision 3).
- New `Common/Interfaces/IPermissionResolver.cs`: `GetEffectivePermissionsAsync(orgId, accountId, ct) : Task<IReadOnlySet<string>>`, `InvalidateMemberAsync`, `InvalidateOrganizationAsync`.
- New `Common/Settings/PermissionResolverSettings.cs`: `{ int CacheTtlSeconds = 60 }`, own config section (sibling to `TenantAccessSettings`).
- New `Services/Roles/` (mirrors `Services/Organizations/`): `IRoleService`/`RoleService` with `ListAsync`, `CreateAsync`, `UpdateAsync`, `DeleteAsync`, `SeedSystemRolesAsync(organizationId, ct)`.
  - `SeedSystemRolesAsync` must **not** call `SaveChangesAsync` — only stages adds via the injected `IUnitOfWork`, so `OrganizationService.CreateAsync` can cover org + roles + role-permissions + member + member-role in one atomic `SaveChangesAsync`. A mid-create failure must not leave an org with zero roles.
  - `CreateAsync`/`UpdateAsync` validate org-scoped name uniqueness (mirrors the Slug check in `OrganizationService.CreateAsync`) and that every submitted permission code exists in `Permissions.All`; reject mutation of system roles with `ForbiddenException`. `UpdateAsync` replaces `RolePermission` rows wholesale (delete-then-insert). `DeleteAsync` relies on FK cascade for cleanup. Both invalidate `IPermissionResolver` for the org after save.
  - `RoleDto(Guid Id, string Name, bool IsSystem, IReadOnlyList<string> PermissionCodes)` — `IsSystem` computed from `SystemRoleKind is not null`; the Owner row's `PermissionCodes` is set to `Permissions.All` explicitly at mapping time (no stored rows to read).
- New `Services/Permissions/`: `PermissionDto(string Code)`, `IPermissionCatalogService`/`PermissionCatalogService` — trivial mapping of `Permissions.All`.
- Edit `OrganizationService.cs` — replace every existing imperative check:
  | Current | Replacement |
  |---|---|
  | `EnsureActiveMemberAsync` | Unchanged — active membership only, no permission gate |
  | `EnsureManagerAsync` (gates Add/UpdateRole/RemoveMember) | `EnsurePermissionAsync(orgId, accountId, Permissions.OrganizationMembersManage)` |
  | Inline `member.Role != Owner` in `DeactivateAsync` | `EnsurePermissionAsync(orgId, accountId, Permissions.OrganizationManage)` |
  | `EnsureNotLastOwnerAsync` | Rewritten against the new model: find the org's Owner-kind `Role`, list `OrganizationMemberRole` for it, list active members, count excluding the one being changed — same in-memory-join style already used elsewhere in this service |
  - `UpdateMemberRoleAsync` → `UpdateMemberRolesAsync(orgId, accountId, UpdateMemberRolesRequest, ct)`: validates `RoleIds` non-empty and all belong to the org; if the member currently holds Owner and the new set doesn't, runs the rewritten last-owner check; replaces `OrganizationMemberRole` rows wholesale; invalidates both `tenantAccessService` and `permissionResolver`.
  - `AddMemberAsync`: `Role` → `RoleIds`; inserts `OrganizationMemberRole` rows after creating/reactivating the member.
  - `CreateAsync`: calls `roleService.SeedSystemRolesAsync` (no intermediate save), links the new member to the seeded Owner role, single `SaveChangesAsync` for everything.
  - **N+1 avoidance** (required, not optional — the generic repo can't do a 4-table hop cheaply): `GetMembersAsync` batch-fetches `OrganizationMemberRole` by member-ids then `Role` by role-ids (2 extra queries total, not N) and stitches role names in memory. `ListMineAsync` batch-fetches `OrganizationMemberRole` → `Role` → `RolePermission` by membership-ids (3 extra queries) rather than calling `IPermissionResolver` once per membership; applies the same Owner short-circuit rule locally. `IPermissionResolver` remains the sole enforcement path (`EnsurePermissionAsync`); this batched read is display data only, not a security boundary.
- Edit `IOrganizationService.cs`, `OrganizationDto.cs` (`MyRole` → `MyRoleNames`/`MyPermissionCodes`), `OrganizationMemberDto.cs` (`Role` → `RoleIds`/`RoleNames`), `AddMemberRequest.cs` (`Role` → `RoleIds`), rename `UpdateMemberRoleRequest.cs` → `UpdateMemberRolesRequest.cs`.
- Edit `ApplicationMessages.cs` + both `Messages.{resx,en.resx}`: add `OrganizationRoleNotFound`, `OrganizationRoleNameAlreadyExists`, `OrganizationSystemRoleImmutable`, `OrganizationMemberRequiresAtLeastOneRole`, `UnknownPermissionCode`. `OrganizationCannotRemoveLastOwner`/`OrganizationAccessDenied` reused unchanged.
- Edit `AuthResult.cs` / `LoginResponse.cs` (both plain positional records today, `backend/src/StarterKit.Application/Services/Auth/`): add `IReadOnlyList<string> Permissions` (empty when `OrganizationId` is null). Edit `AuthService.cs`: inject `IPermissionResolver`, populate it inside `IssueTokensAsync` when `organizationId is { }`. Edit `AuthController.cs`'s response mapping to pass it through.
- Edit `DependencyInjection.cs` (Application): register `IRoleService`, `IPermissionCatalogService`.

### Infrastructure layer

- New `Services/Auth/PermissionResolver.cs` (`internal sealed class`, mirrors `TenantAccessService.cs` exactly): `GetEffectivePermissionsAsync` wraps a raw `AppDbContext` LINQ join (member → OrganizationMemberRole → Role, `AsNoTracking()`) in `cacheService.GetOrSetAsync(key: $"permissions:{orgId}:{accountId}", ttl, ...)`; short-circuits to `Permissions.All` if any resolved role has `SystemRoleKind == Owner`, else joins to `RolePermission` and returns the distinct set. `InvalidateMemberAsync`/`InvalidateOrganizationAsync` mirror `TenantAccessService`'s `RemoveAsync`/`RemoveByPrefixAsync` calls exactly.
- Edit `AuthExtensions.cs`: register `PermissionResolverSettings` + `IPermissionResolver, PermissionResolver`, next to the existing `ITenantAccessService` registration.
- New EF configs in `Persistence/Configurations/`:
  - `RoleConfiguration.cs`: `ToTable("roles")`, `Name` `HasMaxLength(100)`, `SystemRoleKind` `.HasConversion<string>().HasMaxLength(20)` (nullable), unique index on `(OrganizationId, Name)`, **plus** a Postgres partial unique index on `(OrganizationId, SystemRoleKind)` filtered `WHERE SystemRoleKind IS NOT NULL` — guarantees an org can never have two Owner-kind roles (belt-and-suspenders for the last-owner invariant). Cascade FK to `Organization`.
  - `RolePermissionConfiguration.cs`: `ToTable("role_permissions")`, `PermissionCode` `HasMaxLength(100)`, unique index on `(RoleId, PermissionCode)`, cascade FK to `Role`.
  - `OrganizationMemberRoleConfiguration.cs`: `ToTable("organization_member_roles")`, unique index on `(OrganizationMemberId, RoleId)`, cascade FKs to both parents.
- Edit `OrganizationMemberConfiguration.cs`: remove the `Role` property configuration.
- Edit `AppDbContext.cs`: add the 3 new `DbSet<T>` properties (no auto-discovery — must be added by hand, per existing convention).
- Edit `TenantAccessMiddleware.cs`: add `/api/permissions` to the exemption list (alongside `/api/auth`) so a session with just-revoked org access doesn't get a spurious 403 fetching the static catalog.
- Migrations (`dotnet ef migrations add <Name> --project backend/src/StarterKit.Infrastructure --startup-project backend/src/StarterKit.API`): `AddRbacTables` (schema + SQL backfill per Decision 5), then `DropOrganizationMemberRoleColumn` once no code reads the old column.

### API layer

- Edit `OrganizationsController.cs`: add `GetRoles`/`CreateRole`/`UpdateRole`/`DeleteRole`; change the member-role-update action to bind `UpdateMemberRolesRequest` and call `UpdateMemberRolesAsync`.
- New `PermissionsController.cs`: `[ApiController][Authorize][Route("api/permissions")]`, single `GET` calling `IPermissionCatalogService.ListAsync()`.
