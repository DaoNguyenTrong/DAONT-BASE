# Clean Architecture Cleanup — Service Decomposition + Exception Layering

## Context

Follow-up to the 2026-08-04 Clean Architecture review of `backend/`. The review found the Dependency Rule fully intact at both the `.csproj` `ProjectReference` level and the `using StarterKit.*` source level — no import-direction violations, no circular dependencies. Three lower-severity findings remain, and this plan resolves all three (user confirmed a 3-way split for `AuthService` over a simpler 2-way split — see Part 1):

1. **`AuthService`/`IAuthService`** — God Class (518 LOC, 10 constructor dependencies) + Fat Interface (11 methods).
2. **`OrganizationService`/`IOrganizationService`** — God Class (362 LOC) + Fat Interface (7 methods).
3. **`ApiException`** — carries HTTP `StatusCode`/`Title` and is named after the API layer, but lives in `StarterKit.Domain`. Verified: these exceptions are thrown exclusively by Application/Infrastructure use-case code (7 + 3 files), never by a Domain entity invariant.

None of these are Dependency Rule violations in the build-graph sense — this is a decomposition/naming cleanup, not a layering emergency. Scope is deliberately limited to what was flagged; no further redesign beyond it.

## Verified ground truth

- `AuthService` (`backend/src/StarterKit.Application/Services/Auth/AuthService.cs`) has exactly one caller, `AuthController` (`backend/src/StarterKit.API/Controllers/AuthController.cs`), which already constructs cookie-bearing HTTP responses per action — no business logic to preserve there, only wiring changes.
- Of `AuthService`'s 11 public methods, only `GetSessionsAsync`, `RevokeSessionAsync`, `RevokeOtherSessionsAsync` are self-contained: they touch only `unitOfWork.Repository<RefreshToken, long>()`, `currentUserService` (via the private `GetCurrentAccountId()`), and the private static `ComputeSha256`. None of the other 8 methods call these three or vice versa.
- `SwitchOrganizationAsync` also calls `GetCurrentAccountId()`, so `ICurrentUserService` stays a dependency of `AuthService` even after the session methods move out.
- `ComputeSha256` (private static, `SHA256.HashData` + hex-encode, zero dependencies) is used by both the methods staying in `AuthService` (`VerifyEmailAsync`, `RefreshTokenAsync`, `RevokeTokenAsync`, `IssueTokensAsync`) and the methods moving out (`GetSessionsAsync`, `RevokeOtherSessionsAsync`) — extracting it to a shared static helper avoids duplicating it in both classes.
- **A 2-way split (session methods only) does not clear finding #1 — it only narrows it.** Moving just the 3 session methods out leaves `AuthService` with all 10 constructor dependencies (none are exclusive to the 3 moved methods), ~450 LOC, and 8 interface methods — every metric that triggered the finding is still triggered. User confirmed going further: a **3-way split**.
- **The 3-way split has a real complication**: `VerifyEmailAsync` (which needs to move to a registration-focused service) itself calls the private `IssueTokensAsync` + `ResolveDefaultOrganizationIdAsync` — the exact same "mint tokens for this account" logic that `LoginAsync`/`RefreshTokenAsync`/`ExternalLoginAsync`/`SwitchOrganizationAsync` need and that stays in `AuthService`. Without extracting that logic to a shared collaborator, either the two services duplicate ~50 lines of token-minting code (drift risk — e.g. refresh-token-expiry math diverging) or `RegistrationService` would have to depend directly on `AuthService` (wrong direction — turns a decomposition into inter-service coupling). The correct fix: extract `ITokenIssuer`/`TokenIssuer` (`IssueTokensAsync` + `ResolveDefaultOrganizationIdAsync`, needing only `IUnitOfWork`, `IJwtTokenService`, `IPermissionResolver`, `IOptions<JwtSettings>` — 4 deps) as a shared **internal** collaborator both `AuthService` and `RegistrationService` inject. This is not speculative abstraction — it is the direct, necessary consequence of the split the user chose; without it the split can't be done cleanly.
- **Result, recomputed with `TokenIssuer` in place** (better than the rough "8 deps" estimate floated when this was still an open question):
  - `AuthService` (`LoginAsync`, `RefreshTokenAsync`, `RevokeTokenAsync`, `ExternalLoginAsync`, `SwitchOrganizationAsync`): `IUnitOfWork`, `ICurrentUserService`, `ITokenIssuer`, `ITenantAccessService`, `IPasswordHasher`, `IEnumerable<IExternalAuthProvider>` — **6 dependencies, 5 methods, ~200 LOC**. Method count and LOC now clear their thresholds; dependency count is **1 over** (6 vs. the >5 rule) — credential/token/external-login auth genuinely touches that many collaborators, and splitting `ExternalLoginAsync` out further to shave one dependency would fragment a single "authenticate with credentials" concern for no real cohesion gain. Flagged honestly, not swept under the rug: this is as close to the threshold as this plan gets it.
  - `RegistrationService` (`RegisterAsync`, `VerifyEmailAsync`, `ResendVerificationEmailAsync`): `IUnitOfWork`, `IPasswordHasher`, `IEmailSender`, `IOptions<EmailSettings>`, `ITokenIssuer` — **5 dependencies, 3 methods, ~150 LOC**. Fully compliant.
  - `TokenIssuer` (new, internal): `IUnitOfWork`, `IJwtTokenService`, `IPermissionResolver`, `IOptions<JwtSettings>` — **4 dependencies, 2 methods, ~50 LOC**. Fully compliant.
  - `SessionService` (unchanged from the original 2-way analysis): **2 dependencies, 3 methods, ~60 LOC**. Fully compliant.
- `ITokenIssuer`/`TokenIssuer` are declared `internal` (not `public`) — nothing outside `StarterKit.Application` needs them; `StarterKit.Application.Tests` already has `InternalsVisibleTo` access (`StarterKit.Application.csproj`), so they're fully unit-testable without widening the public surface. `AuthController`/`DependencyInjection.cs` never reference `ITokenIssuer` directly.
- `OrganizationService` (`backend/src/StarterKit.Application/Services/Organizations/OrganizationService.cs`) has one caller, `OrganizationsController`, which **already injects two service interfaces side by side** (`IOrganizationService organizationService, IRoleService roleService`) — adding a third follows an existing, unremarkable pattern in this exact file.
- Of `OrganizationService`'s 7 methods, `AddMemberAsync`, `UpdateMemberRolesAsync`, `RemoveMemberAsync` are the members-management trio. Their exclusive private helpers are `EnsureNotLastOwnerAsync`, `ValidateRoleIdsAsync`, `ReplaceMemberRolesAsync`, `GetSystemRoleAsync`, `IsMemberInRoleAsync` — none of these five are called by `CreateAsync`, `ListMineAsync`, `GetMembersAsync`, or `DeactivateAsync`.
- **Correction to the original review recommendation**: the review suggested moving `GetMembersAsync` into the membership service too. Verified against the actual code that's wrong — `GetMembersAsync` and `ListMineAsync` **share** the private helper `LoadRolesByMembershipIdAsync`, and `ListMineAsync` additionally needs `LoadPermissionCodesByRoleIdAsync`. Moving `GetMembersAsync` out would force duplicating those helpers across two classes. Keeping `GetMembersAsync` in `OrganizationService` avoids that; the three-method split below is a clean cut with no shared private state crossing the boundary.
- Dependency accounting after the split: `OrganizationService` keeps `IUnitOfWork`, `ICurrentUserService`, `ITenantAccessService`, `IPermissionResolver` (both used by `DeactivateAsync`'s cache-invalidation calls), `IRoleService` (used only by `CreateAsync`) — **5 dependencies, 4 methods**, both at or under the rubric's threshold. `OrganizationMembershipService` needs `IUnitOfWork`, `ITenantAccessService`, `IPermissionResolver` (both used by all three mutation methods' cache-invalidation calls) — **3 dependencies, 3 methods**. This split, unlike `AuthService`'s, fully clears the God Class/Fat Interface thresholds on both resulting classes.
- `exception.StatusCode`/`exception.Title` (the abstract members on `ApiException`) have exactly **one** consumer in the entire backend: `ExceptionHandlingMiddleware.cs:30-31`. Every other `.StatusCode` hit in the codebase is either `HttpResponseMessage.StatusCode` (integration test assertions) or ASP.NET Core's own `context.Response.StatusCode` (`TenantAccessMiddleware.cs`, `UserTimeZoneMiddleware.cs`) — confirmed unrelated by inspection, so this refactor cannot change any test's expected HTTP status code, only where the mapping table lives.
- `ApiException` as a type name has exactly **9** references across `backend/src` + `backend/tests` (the 6 subclass files, `ApiException.cs` itself, `ExceptionHandlingMiddleware.cs`, `ApplicationAssert.cs`) — small enough to rename safely with Serena's `rename_symbol` (reliable for backend C#, per `serena.md`).
- `NotFoundException`/`ConflictException`/`UnauthorizedException`/`ForbiddenException` are thrown only from Application (`AuthService`, `OrganizationService`, `AccountService`, `ApiKeyService`, `RoleService`, `FileService`, `AuditLogService`) and Infrastructure (`GoogleAuthProvider`, `MicrosoftAuthProvider`, `LocalFileProvider`) — zero throws from Domain entities. Only `DomainException` is thrown from Domain (9 call sites, all inside `Entity.Update()` methods) — this one genuinely represents a domain invariant and is unaffected in spirit, only in losing its `StatusCode`/`Title` members like its siblings.

### New: `backend/src/StarterKit.Application/Services/Auth/SessionService.cs`

```csharp
public sealed class SessionService(
    IUnitOfWork unitOfWork,
    ICurrentUserService currentUserService) : ISessionService
{
    public async Task<IReadOnlyList<SessionDto>> GetSessionsAsync(
        string? currentRefreshToken,
        CancellationToken cancellationToken)
    {
        Guid accountId = GetCurrentAccountId();
        string? currentTokenHash = string.IsNullOrWhiteSpace(currentRefreshToken)
            ? null
            : TokenHash.Compute(currentRefreshToken);

        IReadOnlyList<RefreshToken> tokens = await unitOfWork.Repository<RefreshToken, long>()
            .ListAsync(token => token.AccountId == accountId, cancellationToken);

        return tokens
            .Where(token => token.IsActive)
            .OrderByDescending(token => token.CreatedAt)
            .Select(token => new SessionDto(
                token.Id,
                token.DeviceInfo,
                token.IpAddress,
                token.IsPersistent,
                currentTokenHash is not null && token.TokenHash == currentTokenHash,
                token.LoginAt,
                token.CreatedAt,
                token.ExpiresAt))
            .ToList();
    }

    public async Task RevokeSessionAsync(long sessionId, CancellationToken cancellationToken)
    {
        Guid accountId = GetCurrentAccountId();
        IRepository<RefreshToken, long> repository = unitOfWork.Repository<RefreshToken, long>();

        RefreshToken? token = await repository.GetByIdAsync(sessionId, cancellationToken);

        if (token is null || token.AccountId != accountId)
        {
            throw new NotFoundException(nameof(RefreshToken), sessionId);
        }

        token.Revoke();
        repository.Update(token);
        await unitOfWork.SaveChangesAsync(cancellationToken);
    }

    public async Task RevokeOtherSessionsAsync(string? currentRefreshToken, CancellationToken cancellationToken)
    {
        Guid accountId = GetCurrentAccountId();
        string? currentTokenHash = string.IsNullOrWhiteSpace(currentRefreshToken)
            ? null
            : TokenHash.Compute(currentRefreshToken);

        IRepository<RefreshToken, long> repository = unitOfWork.Repository<RefreshToken, long>();
        IReadOnlyList<RefreshToken> tokens = await repository
            .ListAsync(token => token.AccountId == accountId, cancellationToken);

        foreach (RefreshToken token in tokens)
        {
            if (token.IsActive && token.TokenHash != currentTokenHash)
            {
                token.Revoke();
                repository.Update(token);
            }
        }

        await unitOfWork.SaveChangesAsync(cancellationToken);
    }

    private Guid GetCurrentAccountId()
    {
        if (!Guid.TryParse(currentUserService.UserId, out Guid accountId))
        {
            throw new UnauthorizedException(ApplicationMessages.AuthenticatedUserRequired);
        }

        return accountId;
    }
}
```

Method bodies moved verbatim from `AuthService.cs` (no logic changes) — delete these 3 methods plus the now-unused private `GetCurrentAccountId` copy from `AuthService.cs` (keep the one in `SessionService`; `AuthService` still needs its own copy since `SwitchOrganizationAsync` calls it too — it's a 6-line private helper already duplicated in spirit across services in this codebase, not worth a shared abstraction for).

## Part 3 — Move `StatusCode`/`Title` out of the Domain exception hierarchy
