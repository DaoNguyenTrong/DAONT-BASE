# Migrate Organization/Role Authorization to ASP.NET Core Policy-Based Model

## Context

`OrganizationService`/`RoleService` currently enforce permission and membership checks imperatively, inline, via private `EnsurePermissionAsync`/`EnsureActiveMemberAsync` helpers that throw `ForbiddenException`. The user explicitly chose (over two lighter alternatives: keeping checks imperative, or a document-only marker attribute) to move enforcement into ASP.NET Core's authorization pipeline via `[Authorize(Policy = ...)]`, backed by a custom `IAuthorizationRequirement` + `IAuthorizationHandler` + dynamic `IAuthorizationPolicyProvider`. Confirmed with the user beforehand: this changes **where** the check happens, not **what** is checked — permission is still resolved every request, the existing `IPermissionResolver`/`ITenantAccessService` short-TTL caches are untouched, and permissions are still never embedded in the JWT.

**New finding surfaced during planning (not part of the original ask, but a real regression if unaddressed):** today, when `EnsurePermissionAsync`/`EnsureActiveMemberAsync` throws `ForbiddenException`, `ExceptionHandlingMiddleware` catches it and writes a `CodedProblemDetails` body (`{status, title, detail, code}`, localized `detail` via `Messages.resx`). Once enforcement moves into `[Authorize(Policy=...)]`, denied requests never throw — ASP.NET Core's built-in `AuthorizationMiddlewareResultHandler` intercepts them before `ExceptionHandlingMiddleware` (which only catches `ApiException`) ever sees them, and — since `Program.cs` never calls `AddProblemDetails()` (confirmed via grep, zero hits) — writes an **empty-body 403** by default. The frontend's `use-api-action.ts` reads `problem.detail` and falls back to a generic message when absent, so every organization-permission-denied error in the UI would silently lose its specific localized message. This plan includes a custom `IAuthorizationMiddlewareResultHandler` to preserve the existing body shape, modeled directly on the existing `AddRateLimiter(...).OnRejected` precedent in `Program.cs:110-122` (same `ApiProblemDetailsFactory.Create`/`WriteAsync` calls, same pattern).

## Verified ground truth

- `Permissions` (`backend/src/StarterKit.Application/Common/Authorization/Permissions.cs`): `OrganizationManage`, `OrganizationMembersManage`, `OrganizationRolesManage`, `Permissions.All`.
- `IPermissionResolver.GetEffectivePermissionsAsync` (`PermissionResolver.cs`) returns an **empty set both when the caller is not an active member AND when they're an active member holding only the zero-permission "Member" role** — these two cases are indistinguishable from the returned set alone (confirmed by reading the implementation).
- `ITenantAccessService.HasActiveAccessAsync(Guid accountId, Guid organizationId, CancellationToken)` (`TenantAccessService.cs`) — separately cached, correctly distinguishes "not a member" from "active member" — the right primitive for membership-only checks (`GetMembers`/`GetRoles`).
- `ICurrentUserService.UserId` (`CurrentUserService.cs`) reads `ClaimTypes.NameIdentifier` via `IHttpContextAccessor` — reuse rather than reading the claim directly.
- `IHttpContextAccessor` already registered (`Program.cs:101`) and already consumed inside `StarterKit.Infrastructure` (`CurrentUserService`, `CurrentTenantProvider`, `UserTimeZoneProvider`, `AppDbContext`) — an established, unremarkable pattern here.
- Pipeline order (`Program.cs:151-183`): no explicit `UseRouting()` — ASP.NET Core auto-inserts routing at the very start when it's omitted, so `HttpContext.Request.RouteValues` is already populated by the time `UseAuthorization()` (line 181) runs. No pipeline reordering needed.
- **Hard layering constraint**: `StarterKit.Application.csproj` has zero ASP.NET Core package references (only `Microsoft.Extensions.*.Abstractions` + Mapperly) — fully framework-agnostic. `Microsoft.AspNetCore.Authorization` types are already used inside `StarterKit.Infrastructure/Services/Auth/AuthExtensions.cs`. **New requirement/handler/policy-provider types must live in `StarterKit.Infrastructure`**, matching the precedent of `ApiKeyAuthenticationHandler.cs` (same folder — the closest existing analog, an `AuthenticationHandler` rather than `AuthorizationHandler`). The one exception is the result handler (needs `CodedProblemDetails`/`ApiProblemDetailsFactory`, API-layer types) — that one lives in `StarterKit.API`.
- Zero `IAuthorizationHandler`/`IAuthorizationPolicyProvider`/`IAuthorizationMiddlewareResultHandler` exist anywhere in the codebase today — this is the first of each.
- `OrganizationsController.cs` — 11 actions, class-level `[Authorize]` only; `{id:guid}` is the org-id route segment, consistently named across every action.
- Confirmed via search: `OrganizationsController.cs` is the **only** caller of `GetMembersAsync`/`ListMineAsync`/`RoleService.ListAsync` anywhere in `backend/src` — safe to delete the in-service checks entirely once the policy attribute lands, no other caller left unprotected.

## New types

All under `backend/src/StarterKit.Infrastructure/Services/Auth/` except the result handler.

1. **`OrganizationPermissionRequirement.cs`** — `internal sealed class OrganizationPermissionRequirement(string permissionCode) : IAuthorizationRequirement { public string PermissionCode { get; } = permissionCode; }`

2. **`OrganizationMembershipRequirement.cs`** — `internal sealed class OrganizationMembershipRequirement : IAuthorizationRequirement { }` (marker, no data).

3. **`AuthorizationPolicies.cs`** — `public static class AuthorizationPolicies { public const string OrganizationMember = "OrganizationMember"; }` — must be `public` since `StarterKit.API` references it directly in `[Authorize(Policy = AuthorizationPolicies.OrganizationMember)]`.

4. **`RouteOrganizationId.cs`** — shared route-value extraction, used by both handlers below (don't duplicate the parsing):

   ```csharp
   internal static class RouteOrganizationId
   {
       public static bool TryGet(IHttpContextAccessor accessor, out Guid organizationId)
       {
           object? value = accessor.HttpContext?.Request.RouteValues["id"];
           return Guid.TryParse(value?.ToString(), out organizationId);
       }
   }
   ```

5. **`OrganizationPermissionAuthorizationHandler.cs`**:

   ```csharp
   internal sealed class OrganizationPermissionAuthorizationHandler(
       IHttpContextAccessor httpContextAccessor,
       ICurrentUserService currentUserService,
       IPermissionResolver permissionResolver)
       : AuthorizationHandler<OrganizationPermissionRequirement>
   {
       protected override async Task HandleRequirementAsync(
           AuthorizationHandlerContext context, OrganizationPermissionRequirement requirement)
       {
           if (!RouteOrganizationId.TryGet(httpContextAccessor, out Guid organizationId)
               || !Guid.TryParse(currentUserService.UserId, out Guid accountId))
           {
               return; // leave un-succeeded, not Fail() — don't short-circuit other requirements
           }

           IReadOnlySet<string> permissions = await permissionResolver.GetEffectivePermissionsAsync(
               organizationId, accountId, httpContextAccessor.HttpContext!.RequestAborted);

           if (permissions.Contains(requirement.PermissionCode))
           {
               context.Succeed(requirement);
           }
       }
   }
   ```

6. **`OrganizationMembershipAuthorizationHandler.cs`** — same shape, `AuthorizationHandler<OrganizationMembershipRequirement>`, injects `ITenantAccessService` instead of `IPermissionResolver`, calls `HasActiveAccessAsync(accountId, organizationId, ct)`, succeeds if `true`. Uses `ITenantAccessService`, not `IPermissionResolver` — the resolver's empty set is ambiguous between "not a member" and "member with zero permissions" (see Verified ground truth above).

7. **`OrganizationPermissionPolicyProvider.cs`**:

   ```csharp
   internal sealed class OrganizationPermissionPolicyProvider(
       IOptions<AuthorizationOptions> options) : IAuthorizationPolicyProvider
   {
       private readonly DefaultAuthorizationPolicyProvider fallback = new(options);

       public Task<AuthorizationPolicy> GetDefaultPolicyAsync() => fallback.GetDefaultPolicyAsync();
       public Task<AuthorizationPolicy?> GetFallbackPolicyAsync() => fallback.GetFallbackPolicyAsync();

       public Task<AuthorizationPolicy?> GetPolicyAsync(string policyName)
       {
           if (Permissions.All.Contains(policyName))
           {
               AuthorizationPolicy policy = new AuthorizationPolicyBuilder()
                   .AddRequirements(new OrganizationPermissionRequirement(policyName))
                   .Build();
               return Task.FromResult<AuthorizationPolicy?>(policy);
           }

           return fallback.GetPolicyAsync(policyName);
       }
   }
   ```

   Falls through to `DefaultAuthorizationPolicyProvider` for the statically-registered `AuthorizationPolicies.OrganizationMember` policy and for the bare default `[Authorize]` policy.

8. **`backend/src/StarterKit.API/Authorization/AuthorizationResultHandler.cs`** (API layer — needs `CodedProblemDetails`/`ApiProblemDetailsFactory`):

   ```csharp
   internal sealed class AuthorizationResultHandler : IAuthorizationMiddlewareResultHandler
   {
       private static readonly AuthorizationMiddlewareResultHandler Default = new();

       public async Task HandleAsync(
           RequestDelegate next, HttpContext context, AuthorizationPolicy policy, PolicyAuthorizationResult authorizeResult)
       {
           if (!authorizeResult.Forbidden)
           {
               await Default.HandleAsync(next, context, policy, authorizeResult);
               return;
           }

           IStringLocalizer<Messages> localizer = context.RequestServices.GetRequiredService<IStringLocalizer<Messages>>();
           CodedProblemDetails problemDetails = ApiProblemDetailsFactory.Create(
               localizer, StatusCodes.Status403Forbidden, "Forbidden", ApplicationMessages.OrganizationAccessDenied);

           await ApiProblemDetailsFactory.WriteAsync(context, problemDetails, context.RequestAborted);
       }
   }
   ```

   Delegates Challenge (401) and Success straight to the real handler — 401 behavior (already framework-default via class-level `[Authorize]` today) is unchanged. Only intercepts `Forbidden`. One handler covers all 9 migrated endpoints since both existing imperative checks throw the exact same `ForbiddenException(ApplicationMessages.OrganizationAccessDenied)` today.

## Service edits

**`OrganizationService.cs`**: delete the `EnsurePermissionAsync`/`EnsureActiveMemberAsync` private methods and their single call-site lines at the top of `GetMembersAsync`, `AddMemberAsync`, `UpdateMemberRolesAsync`, `RemoveMemberAsync`, `DeactivateAsync`. `IPermissionResolver` stays injected — still needed for `InvalidateMemberAsync`/`InvalidateOrganizationAsync` calls after mutations; only the enforcement call is removed.

**`RoleService.cs`**: identical treatment — delete both helpers and their call sites in `ListAsync`, `CreateAsync`, `UpdateAsync`, `DeleteAsync`. `IPermissionResolver` stays injected for `InvalidateOrganizationAsync`.
