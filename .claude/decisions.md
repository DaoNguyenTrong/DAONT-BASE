## Repurposed FeedbackHub into a generic app starter (`StarterKit`): dropped multi-tenancy, kept the rest

User wanted this repo cleared to an app-starter baseline for future projects. Multi-tenancy (`Tenant`/`TenantMembership`/`TenantRole`, `X-Tenant-Id` header, `ICurrentTenantService`/`ITenantContextResolver`, `TenantMiddleware`, `TenantsController`) was removed entirely — confirmed via full-codebase mapping that it was bolted on as an isolated vertical slice (own entity/service/controller/middleware/DI lines) with zero coupling into Auth/Account/ApiKey/AuditLog/Files/SystemSettings, so removal was low-risk. Kept: email+password auth (mandatory email verification), Google social login, session management, Account/Profile, ApiKey, AuditLog, Files, SystemSettings.

Renamed `FeedbackHub`/`FEEDBACK-HUB`/`feedback-hub` → `StarterKit` everywhere (namespaces, `.sln`/`.csproj`, DB name, JWT issuer/audiences, email from-name, frontend package name) — a repo-wide mechanical token rename, not a symbol rename, so handled as combined code+config edits rather than via `gitnexus_rename`. Squashed the 7 existing EF migrations into a single `InitialCreate` (no value in preserving FeedbackHub-era schema history for a template repo). Added root `docker-compose.yml` (Postgres + Mailpit) since the mandatory-email-verification design (see "Reverses 'Social login sau MVP'" below) had no seeder and no real SMTP wired for local dev — this fulfills that entry's own "recommend Mailpit for local dev" note, which had never actually been implemented. Rejected keeping tenancy behind a feature flag — no consumer of this template asked for it, and adding it back later is cheaper than carrying dead-but-flagged code.

Also deleted the FeedbackHub-product-specific docs (`shared/docs/architecture/FeedbackHub-*.md`, `shared/docs/api/{api-tenants,integration-tenants}.md`, `plans/v1/{phase 1. Tenancy Core,phase-2-membership-operations}.md`, `plans/implements/02. Import FEEDBACK-HUB-FE.md`) and rewrote `README.md`/`CHANGELOG.md` as generic starter-kit docs — none of it described code that still exists after the removal above.

## Session management endpoints: "revoke others" keeps the calling session alive, not a literal "revoke all"

Added `GET/DELETE/POST /api/auth/sessions[/{id}|/revoke-others]` on top of the existing `RefreshToken` rows (one row per login/refresh, already carrying `DeviceInfo`/`IpAddress`/`IsPersistent`) — no new entity needed. `AuthService` gained `ICurrentUserService` as a constructor dependency (previously didn't need the authenticated identity at all, since login/refresh/logout all resolve the account from the token itself) to scope session queries/revokes to the caller's own `AccountId`.

Explicit product call (asked user, since it materially changes behavior and wasn't derivable from the request): `revoke-others` excludes the session making the request (matches Google/GitHub's "sign out of other devices"), not a literal revoke-all that would force the caller to also re-login. "Current session" is identified by hashing the `refresh_token` cookie on the request and matching it against stored `TokenHash`; if that cookie is absent (non-browser caller), nothing can be excluded and the call degrades to revoking everything — accepted as a reasonable edge case, not worth a separate error.

`RevokeSessionAsync` returns 404 (`NotFoundException`), not 403, when the session ID exists but belongs to another account — standard IDOR mitigation (don't confirm existence of another user's resource).

## RefreshToken now stores SHA-256 hash (`TokenHash`), not plaintext — mirrors `EmailVerificationToken`, breaks existing sessions on deploy

Closed the plaintext-refresh-token tech debt flagged in the "Reverses 'Social login sau MVP'" entry below: `RefreshToken.Token` → `RefreshTokenParams.TokenHash`/`RefreshToken.TokenHash`, hashed with the same `SHA256.HashData` + lowercase-hex pattern `AuthService` already uses for `EmailVerificationToken`. `AuthService.IssueTokensAsync` hashes the raw token before persisting; `RefreshTokenAsync`/`RevokeTokenAsync` hash the incoming raw token before the DB lookup. The raw token is unchanged everywhere else (cookie, response body, `AuthResult.RefreshToken`) — only what's persisted changed, so no frontend/API-contract change was needed.

Migration `HashRefreshTokenValue` scaffolded as drop-`Token`-column + add-`TokenHash`-column (EF treats a rename+type-change as replace, not `RenameColumn`) — added an explicit `DELETE FROM refresh_tokens;` at the top of `Up()` because the scaffolded `AddColumn` defaults existing rows to `TokenHash = ""`, which would collide on the new unique index for any environment with more than one pre-existing row. Accepted trade-off: **every active session is logged out on deploy** (old plaintext values can never match a freshly computed hash) — acceptable pre-launch, called out explicitly since there's no soft-migration path for tokens that were never hashed to begin with.

Also extended `RepositoryPredicateStub` (test helper, previously `IRepository<T, Guid>`-only) with a `long`-keyed overload so `RefreshTokenAsync`/`RevokeTokenAsync` tests could seed a real hashed token and let the predicate actually filter — same rigor `VerifyEmailAsync`'s tests already applied via `ComputeSha256(rawToken)`, previously skipped for `RefreshToken` only because the generic constraint didn't fit its `long` key.

## Google button: custom branding-guideline markup + `prompt()`, not `renderButton()`

Replaced `google.accounts.id.renderButton()` (Google's own rendered widget) with a hand-built `gsi-material-button` (Google's official Material button HTML/CSS from their branding-guidelines generator, user-supplied) wired to `google.accounts.id.prompt()` on click, since the backend's `GoogleAuthProvider` (`GoogleJsonWebSignature.ValidateAsync`) requires the One Tap/GSI **ID-token credential flow**, not the OAuth2 access-token flow (`google.accounts.oauth2`) — so switching to `initTokenClient`/popup for a "real" custom button wasn't an option without also rewriting the backend validation. `initialize()`'s `callback` is unchanged; only the trigger changed. Known trade-off vs. `renderButton()`: `prompt()` is subject to Google's own One Tap moment/cooldown suppression (e.g. `isNotDisplayed()`/`isSkippedMoment()` if the user dismissed it recently), so the click may occasionally not surface a picker — `renderButton()`'s own DOM button doesn't have this failure mode. Accepted per explicit user direction to use this exact style; not yet handling the suppressed-moment case in the UI (no visible fallback/error when `prompt()` silently no-ops).

## `ProfileDto.HasPassword`: derived via Mapperly user-mapping method, not manual construction after the generated call

Client needs to know whether the current account has a local password (to hide the change-password form for Google-only accounts, where `Account.PasswordHash` is null). Added `HasPassword` to `ProfileDto` and mapped it in `EntityMapper.ToProfileDto` via `[MapProperty(nameof(Account.PasswordHash), nameof(ProfileDto.HasPassword))]` plus a private `MapPasswordHashToHasPassword(string?) => bool` method — Mapperly 4.3.1 auto-detects and uses same-class methods matching the source/target types for a mapped property when the types aren't directly convertible. Rejected: splitting into a Mapperly-generated "core" method (`[MapperIgnoreTarget]`) plus a public wrapper using `with { HasPassword = ... }` — fails at compile time (`RMG013`) because `ProfileDto` is a record with only its primary constructor, so Mapperly can't omit a required positional parameter from the generated call. First use of this user-mapping-method pattern in `EntityMapper`; reuse it for future derived/computed DTO fields instead of the `with` pattern.

Also fixed in passing: `frontend/.env.example`'s `VITE_API_BASE_URL` had a stray `/api` suffix that double-prefixes every request path (`apiClient` already prepends `/api/...` itself) — found and worked around with a scratch override during Phase 2 live-testing but never fixed at the source until now.

## `w-full` (and any Tailwind utility) silently loses to naive-ui's own CSS on shared properties — needs `!` important, not just style order

Found while investigating misaligned submit buttons: `<n-button class="w-full">` doesn't actually render full-width. Root cause is specific to this stack (Tailwind v4 + naive-ui), not a generic specificity bug: Tailwind v4 wraps all utilities in `@layer utilities`, and per the CSS spec **any unlayered rule always beats any layered rule, regardless of selector specificity or document order**. naive-ui injects its component styles as plain unlayered `<style>` tags at runtime, so `.n-button { width: var(--n-width) }` always wins over `.w-full { width: 100% }` on the same element — reordering when naive-ui's styles get inserted (see the `naive-ui-style` anchor meta tag decision above) cannot fix this, only `!important` can. Verified live: `!w-full` (Tailwind v4's important-prefix syntax) renders correctly; `w-full` alone does not, no matter where in `<head>` naive-ui's styles land.

Rolled out to `LoginView.vue` and (2026-07-22) `RegisterView.vue` — both confirmed live via screenshot (button now spans full card width, matching the inputs). Still pending on any other `n-button.w-full` pairing found elsewhere (e.g. `ProfileDialog.vue`'s two submit buttons still use plain `min-h-11 w-full`) — apply the same `w-full` → `w-full!` swap there whenever that page/component is next touched, rather than as a standalone sweep.

## Frontend `renderComponent` test helper: push+await the initial route before mount, not after

`VerifyEmailView` reads `route.query.token` synchronously inside `onMounted` — a component-level pattern with no precedent elsewhere in the codebase (no view previously read query params at all). The test helper (`frontend/tests/helpers/render.ts`) originally only set `createMemoryHistory({ initialEntries: [...] })` and awaited `router.isReady()` *after* `mount()`. That looked correct and even produced two false-positive passing tests (assertions that happened to hold regardless of the bug), but `route.query` was actually `{}` in every test — `initialEntries` alone doesn't get reflected into `router.currentRoute`/`route.query` until an explicit navigation resolves, and `onMounted` runs synchronously during `mount()`, before `router.isReady()` (awaited afterward) had a chance to. Root-caused by literally logging `route.query` inside the component under test and diffing across the "passing" vs "failing" tests, since `isReady()`-after-mount looked like it should have been sufficient. Fix: explicitly `await router.push(initialRoute)` then `await router.isReady()` *before* calling `mount()`. Any future test needing `route.query`/`route.params` at mount time must go through the `initialRoute` option this way, not just `initialEntries`.

While fixing the above, live browser testing (not caught by unit tests, which always mount a fresh component instance) surfaced a second, real bug in `VerifyEmailView`: navigating between two different `/verify-email?token=...` URLs via an in-app hash change (no full page reload) reuses the existing component instance — vue-router doesn't remount a route's component just because its query changed — so an `onMounted`-only implementation only ever processes the *first* token it saw. Fixed by moving the logic into `watch(() => route.query.token, ..., { immediate: true })` instead of `onMounted`. Low real-world impact (a genuine email-link click is always a fresh external navigation), but cheap to fix correctly and makes the component's behavior match what "driven by the route" actually implies.

## Frontend runtime config (`public/config.json`): overrides axios `defaults.baseURL` post-creation, doesn't touch `client.ts`'s module-level `axios.create()`

Added deploy-time API base URL override so one build can target different backends without a rebuild: `main.ts`'s `bootstrap()` calls `loadRuntimeConfig()` (fetches `/config.json`, a plain `public/` static file — not processed by Vite, gitignored, `public/config.example.json` documents the shape) *before* `restoreSession()`, and only mutates `apiClient.defaults.baseURL`/`refreshClient.defaults.baseURL` if a valid `apiBaseUrl` came back; otherwise the build-time `VITE_API_BASE_URL` already set at module load (`client.ts`'s `axios.create({baseURL: import.meta.env.VITE_API_BASE_URL, ...})`) is left untouched. Deliberately did **not** restructure `client.ts` itself (e.g. deferring `axios.create()` until after config loads) — that would change `apiClient`'s `baseURL` from `''` to `undefined` in tests (`vitest.config.ts` sets `VITE_API_BASE_URL: ''`), an unnecessary risk to already-passing test behavior for a change that doesn't need it.

Live-testing this locally surfaced a non-obvious gotcha, not a bug in the feature itself: `vite.config.ts`'s `server.watch.ignored` already excludes `**/public/**` (pre-existing, not something this change added) — Vite's dev server resolves its static-file list from `public/` at *startup*, so a `public/config.json` created after `bun run dev` is already running 404s (silently falls through to the SPA index.html fallback, not an error) until the dev server is restarted. Irrelevant in real deploys (a fresh static-file server reads the real filesystem per request), but real enough during local testing that it's called out in the README next to the feature's usage instructions.

## Unified error envelope: shared `ApiProblemDetailsFactory`, not literal exception-routing

Three error sources produced structurally different JSON: `ExceptionHandlingMiddleware` (exceptions → `{status,title,detail}`), ASP.NET Core's automatic `[ApiController]` model validation (→ `ValidationProblemDetails` with `errors`, English-hardcoded top-level title), and the rate limiter's `OnRejected` (hand-written anonymous object, hardcoded English, bypassing localization entirely). Rejected literally forcing all three through the middleware via thrown exceptions — validation and rate-limiting aren't exceptional control flow, and `OnRejected`'s exception-propagation-to-upstream-middleware behavior is unverified/fragile to depend on. Instead: one `ApiProblemDetailsFactory.Create`/`CreateValidation` (API layer, `IStringLocalizer<Messages>`-backed) called from all three entry points, plus a `code` field (= the message's resx key, e.g. `EmailNotConfirmed`) so the frontend can branch on error identity instead of parsing localized prose — the original ask (FE can't distinguish `EmailNotConfirmed` from a bad password, both 401) is what motivated adding `code` at all.

`code` is a normal property on new `CodedProblemDetails`/`CodedValidationProblemDetails` (subclassing `ProblemDetails`/`ValidationProblemDetails`), **not** `ProblemDetails.Extensions` — `Extensions` is `[JsonExtensionData]` using the *System.Text.Json* attribute, which Newtonsoft (used for the validation path via `AddNewtonsoftJson()`) doesn't recognize, so it would've nested as `{"extensions":{"code":...}}` there while flattening elsewhere — verified live via curl, not assumed. Also hit and fixed two `WriteAsJsonAsync` gotchas verified live: (1) it infers the STJ contract from the *declared* type of the call-site expression, not the runtime type — a `WriteProblemAsync(HttpContext, ProblemDetails problemDetails)` helper silently drops derived-only properties like `Code`, so the write helper must be generic (`WriteAsync<T>` where `T : ProblemDetails`, inferred per call site); (2) `WriteAsJsonAsync(value, cancellationToken)` overwrites `Response.ContentType` to `application/json` even if set beforehand — the content-type must be passed as an explicit argument to the overload that accepts one. Removed dead `TooManyRequestsException` (never thrown; 429 came from `OnRejected`, not application code) and the frontend's stale `errors.tokenQuotaExhausted` 429 override (mislabeled leftover from the old chat/RAG token-quota feature — the backend's `detail` is now real and localized, so the client no longer needs to override it).

Not done: sweeping the ~74 `[ProducesResponseType(typeof(ProblemDetails)/typeof(ValidationProblemDetails), ...)]` annotations across controllers to the new coded subtypes — they remain accurate (subtype *is-a* base type) but Swagger schemas won't show `code` until that mechanical sweep happens; low priority while `shared/openapi/` codegen isn't wired up yet.

## Reverses "Social login sau MVP": mandatory email verification + SMTP now, social login (Google-first) next

User asked to upgrade register now: email verification is **mandatory** (register no longer auto-issues tokens; `POST /api/auth/login` throws 401 `EmailNotConfirmed` until the account verifies) and real SMTP is required in every environment, including dev — no auto-confirm bypass. This directly overrides the earlier "Social login để sau MVP" entry below. Rationale for no dev-bypass: the register → verify-email → login loop is the *only* account-bootstrap path (no seeder, no admin UI yet), so a bypass would just move the chicken-and-egg problem instead of fixing it; recommend Mailpit/MailHog for local dev (real SMTP protocol, no external delivery).

Verification token stored as SHA-256 hash (`EmailVerificationToken.TokenHash`), not plaintext — deliberately *not* copying `RefreshToken`'s existing plaintext-in-DB pattern, which stays as-is (pre-existing tech debt, out of scope here).

Social login: chose credential-forwarding (FE gets id_token/code from provider SDK, POSTs to BE for validation) over server-driven OAuth redirect — decouples BE from FE hosting/redirect-URI concerns and is testable standalone before any FE work exists. Google shipped first (self-verifiable id_token via `Google.Apis.Auth`, no secret needed); Microsoft/GitHub deferred behind the same `IExternalAuthProvider` abstraction. Both phases now shipped and verified live (real SMTP round-trip via Mailpit; real Google.Apis.Auth call rejecting a malformed credential). `ExternalAuthSettings:Google:ClientId` is optional at startup — an unconfigured provider is simply not registered (`ExternalLoginProviderNotSupported` at call time) rather than blocking app boot for everyone, unlike `EmailSettings` which fails fast (email is load-bearing for bootstrap; social login isn't).

Post-implementation review caught a takeover gap: `ExternalUserInfo` didn't carry the provider's `email_verified` claim, so an attacker-controlled Google identity asserting an unverified email could auto-link to (or spoof-create) an account matching that email, bypassing the local `EmailConfirmed` check entirely — the account-confirmed check guarded the wrong side of the trust boundary. Fixed by adding `EmailVerified` to `ExternalUserInfo`, populating it from `payload.EmailVerified` in `GoogleAuthProvider`, and rejecting (`UnauthorizedException`) in `AuthService.ExternalLoginAsync` before any match/link/create if the provider didn't verify the email.

## `== default` is never a valid required-check for an enum whose first member is the meaningful default

Historical lesson from this codebase (originally caught in the now-removed `TenantMembership.Role` validation, since deleted along with multi-tenancy — see the StarterKit-baseline entry above): a check like `if (p.Role == default) throw` silently rejects the *first* enum member whenever that member's underlying value is `0` (C#'s implicit enum default) — e.g. an enum `{ Owner, Member }` makes `Owner == 0 == default`, so "require a role" ends up rejecting the exact value most likely to be assigned by default. This passed build and the full test suite despite being wrong, because nothing exercised that code path — only caught by a test written specifically to cover the "assign the first enum member" case. Fix: validate with `!Enum.IsDefined(p.Role)` instead, or add an explicit `Unspecified = 0` sentinel if `default` genuinely shouldn't be a valid value.
